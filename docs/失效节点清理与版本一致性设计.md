# 失效节点清理与版本一致性设计

> 目标：解决两件事 —— ① **误启动 / 注册失败的节点会永远留在父端的注册表与库里，需要一个命令把它们清掉**；
> ② **全集群的可执行文件版本必须唯一**，给出"版本控制"该如何组织。
>
> 状态：**已实施 P0–P2（接口与存储原语）**，见第 7 节。代码位置：
> `POST/GET /v1/forget`（`internal/node/forget.go` + `internal/node/api.go`）、
> `store` 的三个按子删除原语（`internal/store/store.go`）、`forget` 配置段（`internal/config/config.go`）、
> README「失效节点清理：`/v1/forget`」。剩余 P3（`/v1/tree` 可见性与健康分母）与 P4（版本缺口）待做。
>
> 重要前提：② 的**运行期能力已经实现**（哈希上报 + 不一致即自同步 + 三重校验 + 原地 `exec` 重启，
> 见 README「可执行文件一致性」与 `internal/node/build.go`），本文**不重复设计**，只列缺口。
>
> 本文所有结论都标注了 `文件:行号`，均为在当前 `HEAD=cd152fa` 上**实际打开源码核对**的结果。

## 结论速览

| # | 条目 | 定性 | 风险 | 建议动作 | 优先级 |
|---|------|------|------|----------|--------|
| 1 | 断连后注册表不删（`registry.Remove` 是**死代码，零调用**） | **真缺陷** | 高：残留子永远出现在 `/v1/tree`，且把健康聚合算成长期 DEGRADED | 新增清理命令，激活 `Remove` | **P0** |
| 2 | `state.dat.known_children` 与注册表构成**只增不减的自锁定闭环** | **真缺陷** | 高：清不掉、重启又回来 | 清理后立即 `saveState()` 兜底 | **P0** |
| 3 | 死子的未终态 `assignment` **永久钉住整棵树的 cmdlog 水位** | **真缺陷（连带）** | 中高：`cmdlog` 永不 GC，盘持续涨 | 清理时删掉该子的 assignment（见 §3.4）；`scanEvictions` 待一并修 | **P0（清理侧已做）** |
| 4 | `unaryAudit` → `touchChild` 给"注册失败但调过一元 RPC"的 NodeID 凭空建水位 | **真缺陷** | 中：垃圾水位的来源之一 | 由清理命令覆盖；是否顺带收窄 `touchChild` 待定（见 §2.3） | P1 |
| 5 | `assignments`/`assign_child`/`child_reports`/`evicted_children` **只有按指令删除的原语** | 功能缺口 | 中：清理无原语可用 | 补 3 个按子删除的 store 原语 | **P0** |
| 6 | `Confirmed` 字段**全库只写不读** | 功能缺口 | 中：API 无法区分"掉线真子"与"历史残留" | 清理命令与 `/v1/tree` 开始读它 | P1 |
| 7 | 构建期版本号未注入（`Version="dev"`）、无 `--version`、仓库无 git tag | 工程缺口 | 低：只影响可追溯性，**不参与任何判定** | 加 `Makefile` 注入 + `-version` | P1 |
| 8 | 没有"全树是否已收敛到同一哈希"的显式判定命令 | 运维缺口 | 低：只能人工看 `lagging_children` | 加只读收敛判定 | P2 |
| 9 | 注册时不拒绝 `build_hash != 父` 的子 | 有意取舍 | 低 | 暂不加硬约束（见 §8-4） | P3 |

**一句话**：① 的根因不在"注册流程没清理"，而在 **`registry.children` 只增不减 + `known_children` 每 30s 自我回灌** 这对闭环；
清理必须同时打掉这两环，并顺带解开被死子钉住的 `cmdlog` 水位，否则只是"表面干净"。
② 的运行期机制已经齐备，剩下的只是"构建期有版本号 + 运维能一眼断言全树收敛"。

## 1. 现状审计：失效节点到底残留在哪里

### 1.1 一个子节点的一生（注册成功时的写入点）

| 落点 | 内容 | 证据 |
|---|---|---|
| bbolt `child_watermark` | **注册事务里唯一被写的桶**：新子建 `{ChildId, FetchedCmdSeq=最后分配的 seq, LastSeenAt, LastEpoch}`；老子只刷 `LastEpoch/LastSeenAt` | `internal/node/hub.go:602-632`（写水位 `:621`） |
| 内存 `registry.Table` | `Reg.Upsert(&Child{… Confirmed:true, ListenAddr, BuildHash, LastEpoch})` —— **全库唯一调用点** | `hub.go:654-661` |
| `assignments` / `commands` | 注册时**不写** | — |
| `state.dat` | 注册时**不写**，由 30s 周期任务全量落盘 | `internal/node/node.go:959` |

### 1.2 注册失败的分支会不会留残骸

绝大多数**不留**（都在写库之前 return，或事务内 return 导致回滚）：

| 分支 | 位置 | 残留 |
|---|---|---|
| `CERT_REVOKED` | `hub.go:570-574`（流级）、`hub.go:256-260`（一元） | 无 |
| `ERR_NODE_ID_MISMATCH` | `hub.go:576-578`、`hub.go:292-294` | 无 |
| `ERR_CYCLE` | `hub.go:580-587` | 无 |
| `ERR_UNSUPPORTED_VERSION` | `hub.go:589-591`、`hub.go:213-227` | 无 |
| `STALE_EPOCH` | `hub.go:605-607`（**事务内** return → 回滚） | 无 |
| 入网侧 10 个 `ERR_ENROLL_*` | `internal/node/enroll.go` | 无（只写审计日志与指标） |

**唯一漏点**：`unaryAudit` 在放行前调用 `touchChild(id)`（`hub.go:268` → `internal/node/delivery.go:435-444`），
它**不判断对方是否注册成功**，直接为这个 NodeID 建一条 `child_watermark`。
于是"能过 mTLS、但注册被拒（或根本没走注册）"的对端会留下一条**孤立水位**。
`StreamResult` 路径同理。

### 1.3 永久残留清单（目前**没有任何回收入口**）

| # | 残留 | 为什么清不掉 | 证据 |
|---|---|---|---|
| 1 | 内存 `registry.children` | 子掉线只打日志 + 关连接（`detach`），**不动注册表**；`Table.Remove` 定义了但生产代码零调用 | `registry.go:132-136`（死代码）、`hub.go:686-690` |
| 2 | `state.dat.known_children` | `saveState` 每次用 `Reg.Snapshot()` **全量重建**；启动时 `Reg.Warm()` 又把它们塞回内存表（`Confirmed=false`）→ **自锁定** | `node.go:976-980`、`registry.go:192`、`node.go:222` |
| 3 | 未被标记 `Evicted` 的 `child_watermark` | `cleanupEvicted` **只删 `Evicted==true`** 且超 30d 的 | `lifecycle.go:718-737` |
| 4 | `touchChild` 建出的孤立水位 | 同上（从未 `Confirmed` → 永远不会被标 Evicted？取决于驱逐实现，见 §1.4） | `hub.go:268` |
| 5 | 该子的 `assignments`（含 `assign_child` 反向索引） | **只有 `DeleteAssignmentsOfCommand`（按指令）** | `store.go:465` |
| 6 | 该子的 `child_reports` | **只有 `DeleteChildReportsOfCommand`（按指令）** | `store.go:587` |
| 7 | 该子的 `evicted_children` 归档 | 只按 `ExpireAt` 兜底 GC（30d），无"按子清"入口 | `store.go:991`、`lifecycle.go:723` |
| 8 | `crl` 桶里的吊销 ID | `Revoke` 只能加不能减，**无解除吊销入口** | `internal/node/crl.go:89-116` |

> 驱逐（`scanEvictions`，每 5m，`eviction_timeout` 默认 24h）只做两件事：把该子未终态的指令体归档进
> `evicted_children`、把水位置 `Evicted=true/EvictedAt`。**它不删注册表、不删 assignments、不删 `known_children`。**

### 1.4 连带缺陷：一个死子能永久钉住整棵树的 `cmdlog`

`cleanupCommandLog`（`cancel.go:242`）用 `floor := tx.MinUnfinishedSeq()`（`cancel.go:248`）作为水位下限，
而 `MinUnfinishedSeq`（`store.go:503`）是"**所有未终态 Assignment 里最小的 LocalSeq**"，**没有 `Evicted` 判断**。
`docs/项目功能完整介绍.md` 声称"驱逐的子退出水位计算"，但代码里没有这条分支。

后果：一个掉线/被驱逐的子，只要名下有未终态 assignment（且它的 `FetchedCmdSeq` 很低），
`cmdlog` 就**永远进不了 GC**。所以清理命令**必须**同步收敛这些 assignment，否则清理只是表面的。

### 1.5 症状（运维视角）

| 症状 | 位置 |
|---|---|
| `/v1/tree` 里残留子永远 `online:false`，**没有** `confirmed` / `last_seen` / `evicted` 字段可供区分 | `internal/node/query.go:854-886`（`online` 取自 `hub.conn()`） |
| 健康聚合把 `known`（注册表条数）当分母 → **残留把节点算成长期 DEGRADED** | `internal/node/health.go:158-171` |
| `children_known` / `lagging_children` 被残留污染 | `node.go:814` 一带 |

## 2. 「失效」的判定口径

### 2.1 硬前提

**`hub.conn(childID)` 命中（即当前在线）→ 一律不删，任何模式、`force` 都绕不过。**
理由：在线 = 正在服务，最可能是"滚动重启中途"或"刚重连"，误删它等于制造故障。
`hub.conn()` 与 `/v1/tree` 的 `online` 同源（`hub.go:912`），保证"运维看得见的"与"命令护栏"一致。

### 2.2 两档判定

| 模式 | 条件（均需"不在线"） | 语义 | 默认 |
|---|---|---|---|
| `garbage` | ① `child_watermark` 存在但 `registry.Get` **未命中**（从未成功注册）**或** `Child.Confirmed == false`（仅 `Warm` 预热塞入）；**且** `LastSeenAt` 早于 `forget.grace`（默认 **1h**） | 误启动 / 注册失败产生的垃圾 | ✅ 默认 |
| `stale` | `Confirmed == true` **且** `LastSeenAt` 早于 `forget.dead_threshold`（默认 **24h**，对齐 `eviction_timeout`） | 长期离线的**真子** | 需显式 `mode=stale`，或 `force` 越过 grace |

两个新配置项（对齐既有 `health` / `command` 段的写法）：

```yaml
forget:
  grace: 1h           # garbage 模式的最小"沉默时长"（避免清掉"正在重试注册、马上会成功"的节点）
  dead_threshold: 24h # stale 模式的判定线；默认对齐 health.eviction_timeout
```

### 2.3 为什么不用"注册失败时间"做判定

注册失败**不落盘**（§1.2），所以没有"失败时间"可查。可查的只有 `child_watermark.LastSeenAt`
（`touchChild` 会刷新它）与 `Confirmed`。这正是本口径用这两个字段的原因。

可选增强（P1，非必须）：把 `touchChild` 收窄为"仅对已在注册表内的子刷新水位"，从源头减少孤立水位。
代价是要改动一元 RPC 的审计路径（`hub.go:268`），有回归风险，建议**先上清理命令**、观察一段时间再决定。

## 3. 清理命令设计

### 3.1 为什么是"HTTP 为主 + CLI 薄封装"

运行中的节点**独占 `state.db`**：`store.Open` 用 `bolt.Options{Timeout: 5s}`（`internal/store/store.go:74`），
所以一个**离线的 CLI 进程根本打不开库**，无法自己完成删除。
因此：**真正的删除动作必须在节点进程内、通过 HTTP 触发**；CLI 只负责"读 `node.yaml` 拿 API 地址 → 发 HTTP → 打印结果"。

### 3.2 接口

对齐既有运维动作范式 `POST /v1/crl`（`api.go:250-270` → `crl.go:89-116`：落盘 + 下发 + AUDIT 日志 + 指标）。

| 动作 | 请求 | 行为 |
|---|---|---|
| **预览（dry-run）** | `GET /v1/forget?node=<guid>` | 返回：是否在线 / 是否在注册表 / `Confirmed` / `LastSeenAt` / `Evicted` / 待删的 assignments、reports、evicted 条数 / 本模式是否合格。**不改任何数据** |
| **执行** | `POST /v1/forget?node=<guid>&mode=garbage\|stale&force=1&purge=1` | 真正清理（见 §3.3-3.5）。`force` 用于越过 `grace` 阈值；`purge` 才连 `child_reports` 一起删 |
| **批量** | `POST /v1/forget?all=1&mode=garbage` | 对本节点全部直接子逐条处理，返回逐条结果 |

用 `GET` 做预览、`POST` 才落盘，是刻意的 REST 语义：预览天然幂等只读，`force=1` 充当二次确认。
比"POST 默认 dry-run + `--apply`"更贴合本仓库 `/v1/crl` 的既有习惯。

CLI 侧沿用现有 flag 风格（本仓库**没有子命令**，只有 flag）：

```bash
treecmd-node -forget <guid> [-config node.yaml] [-forget-mode garbage|stale] [-forget-force]
treecmd-node -forget-all    [-config node.yaml] [-forget-mode garbage]
```

`main()` 在 `flag.Parse()` 后、`Start()` 前插入分支：命中则**只发 HTTP、打印响应、退出**，不启动节点、不开 bbolt。

### 3.3 清理动作清单与所需原语

| 目标 | 动作 | 用什么 |
|---|---|---|
| 内存注册表 | `Reg.Remove(childID)` | **已有**（`registry.go:132-136`），本次激活它的**第一个生产调用点** |
| `assignments` + `assign_child` | 先收敛（§3.4）再删该子全部条目 | **新增** `DeleteAssignmentsOfChild(childID)`；枚举复用已有 `CommandIDsOfChild(childID)` |
| `child_watermark` | 删该子水位 | **已有** `DeleteWatermark`（`store.go:1021`） |
| `evicted_children` | 删该子归档 | **新增** `DeleteEvictedOfChild(childID)` |
| `child_reports` | 仅 `purge=1` 时删 | **新增** `DeleteChildReportsOfChild(childID)` |
| `commands` / `cmdlog` | **不删** | 删掉 assignment 后 `MinUnfinishedSeq` 自然抬升，交给既有 GC |
| `state.dat.known_children` | 删完立即 `saveState()` 兜底 | **已有**（`node.go:959`） |

**两处关键澄清（实现前必须知道）**：

1. **`assign_child` 的键是 `childID/commandID`**（`store.go:389`，它是 `assignments` 的反向索引，
   而 `assignments` 的键才是 `commandID/childID`）。所以**可以**按子前缀扫，`CommandIDsOfChild`
   （`store.go:444` 一带）已经这么做了 —— 删该子的 assignments 实现很简单，**不需要新建索引**。
2. **`child_reports` 的键是 `commandID/childID`**（`store.go:554`），**不能**按子前缀扫 ——
   只能全桶遍历按 `ChildId` 过滤。这是本方案里**唯一有性能代价**的删除点（见验收里的规模用例）。

### 3.4 未终态 Assignment：直接删除即可（**实施时修正**）

实施时确认：**在同一个写事务里，"先把未终态 assignment 收敛为 `CANCELLED` 再删"是空操作** ——
`MinUnfinishedSeq`（`store.go:503`）统计的是"仍然存在的未终态 assignment"，把它删掉就等于把它移出
未完成集合、水位自然推进；而事务进行期间没有任何其他协程能观察到那个中间状态。

所以实现取**纯删除**，它同时解决了原本担心的两件事：

- 解开 §1.4 的"死子钉住 cmdlog"：该 assignment 不再存在 → `MinUnfinishedSeq` 抬升；
- 防止该子日后回来 `Reconcile` 重投一条"父已不持有指令体"的 assignment：记录已不存在 → 不会有幽灵指令。

> 已落到代码：`internal/node/forget.go` 的 `Forget` 只做删除、不写中间态。
> 若将来改成"保留 assignment、只标终态"的变体，才需要把收敛步骤加回来。

### 3.5 事务边界与并发

```
① 预检（只读）
     读 conn（内存）/ Reg.Get（内存）/ watermark（Store.View）→ 判定模式是否合格
② 主删除（单条 Store.Update，原子）
     逐条 assignment：非终态则置 CANCELLED 落盘 → 删 assignment + 反向索引
     purge 时删该子 child_reports
     删该子 evicted 归档
     删该子 watermark
③ 事务成功之后（事务外）
     n.Reg.Remove(childID) → n.saveState() → 审计日志 + 指标
```

- `Reg.Remove` **必须**放在事务成功之后：否则会出现"内存已无、盘上还在"，并在 30s 内被周期 `saveState` 写回。
- 锁序：`Store.Update` → `Reg.mu` → `stateMu`，三者不交叉持有，无死锁。
- bbolt 写事务本身保证"要么全删、要么回滚"；失败时内存与 `state.dat` 保持一致（不清）。

### 3.6 护栏 / 审计 / 指标

| 护栏 | 做法 |
|---|---|
| 在线不可删 | `hub.conn()` 命中 → `409 CHILD_ONLINE`，`force` 也绕不过 |
| 默认最保守 | 默认 `mode=garbage`（只清从未 `Confirmed` 的残留）；清"长期离线真子"必须显式 `mode=stale` |
| 预览先看 | `GET` 预览、`POST` 才落盘；越过 `grace` 需要 `force=1` |
| 视图边界 | 只有**直接父**能清理自己的直接子（这些记录只存在于父侧）；整树清理由运维脚本遍历各节点 API 各自执行，**不新增跨节点 RPC** |
| 审计 | 日志 `AUDIT-FORGET`（对齐 `AUDIT-REVOKE`，`crl.go:109`），字段：childID / mode / force / 删前是否在线 / 各桶删除条数 / 保留报告数 |
| 指标 | `forget_total{result=ok\|dry_run\|conflict_online\|not_found\|stale_requires_force}`（对齐 `selfupdate_total{result}` 的命名风格，`metrics.go:81`） |

### 3.7 备选方案（及为什么没选）

| 备选 | 为什么不选 |
|---|---|
| 纯 CLI 离线清理（直接开 bbolt） | 运行中的节点独占 `state.db`（5s 锁超时），**必然失败** |
| 子掉线即自动从注册表删除 | 会误伤"滚动重启中途"的正常子；且丢掉了"曾经有哪些子"的运维信息。**改为显式命令 + 可见性字段** |
| 根逐跳下发"遗忘"指令 | 需要新增跨节点 RPC 与信任放大；而子状态本来就只存在于直接父侧，逐跳下发是把简单问题复杂化 |
| 给 `child_reports` 建反向索引 | 为一次性运维动作增加一个长期维护的索引，不划算；全桶扫描在百级子、万级指令下可接受（见 §3.8） |

### 3.8 验收标准

**正向**

| 用例 | 断言 |
|---|---|
| 清注册失败垃圾 | 只有孤立 watermark、`Reg` 无此子 → 执行后 assignments / watermark / evicted 清空，`Reg` 不含 |
| 清 `Warm` 预热残留 | `Confirmed=false` 的子 → 可清 |
| `known_children` 不再回灌 | 执行后查 `state.dat` 不含该子；**重启节点后仍不含** |
| `cmdlog` 水位解锁 | 造"低位 `FetchedCmdSeq` + 未终态 assignment"的死子 → 清理后 `MinUnfinishedSeq` 抬升、`cleanupCommandLog` 可推进 |
| 报告开关 | 默认保留 `child_reports`；`purge=1` 才删，审计日志记录条数 |

**负向（必须全绿）**

| 用例 | 断言 |
|---|---|
| **在线子不可删** | 构造在线连接 → `409 CHILD_ONLINE`，**所有桶计数不变** |
| **不误删正在滚动重启的子** | `Confirmed=true`、`LastSeenAt` 5m 前（< grace）→ `garbage` 拒绝；`stale` 且 < `dead_threshold` 也拒绝 |
| 事务失败全回滚 | 在 `Store.Update` 内注入错误 → 各桶不变、`Reg` 仍含该子、`state.dat` 仍含 |
| 预览不改数据 | `GET /v1/forget` 后所有桶计数不变 |

**规模**：200 个直接子、其中 50 个失效 → 单次批量清理耗时 < 2s（`child_reports` 全桶扫描是唯一风险点）。

## 5. 版本一致性：已实现的与还缺的

### 5.1 已实现（**勿重复设计**）

| 能力 | 位置 |
|---|---|
| 启动算自身可执行文件 sha256（解析符号链接 + 流式哈希，`sha256:` 前缀自描述） | `internal/buildinfo/buildinfo.go`（`HashPrefix` `:30`、`Version` `:36`） |

| 防重启循环：`state.dat` 的 `self_update{TargetHash, Attempts, …}`，同目标哈希窗口内最多 N 次 | `build.go`、`internal/persist/state.go` |
| 配置段 `selfupdate`（`enabled` / `on_mismatch: sync\|warn` / `serve` / `chunk_size` / `max_bytes` / `sync_timeout` / `max_attempts` / `attempt_window` / `dir`） | `internal/config/config.go:292-420` |
| 观测：`/v1/tree` 每子带 `build_hash`、节点级 `lagging_children`；指标 `selfupdate_total{result}` / `selfupdate_serve_total{result}` / `binary_info{hash}` | `internal/node/query.go`、`internal/observability/metrics.go` |
| 设计原则（**已写在代码注释里**）：**版本号不参与判定，一切判定只看哈希**；`Version` 只用于展示与日志 | `buildinfo.go:12` |

> 这条原则很关键：**"版本唯一"在本系统里的准确表达就是"全树 `build_hash` 相等"**，
> 版本号字符串（如 `v1.2.0`）只是给人看的标签，不做任何判定依据。本节的缺口都遵循这条。

### 5.2 缺口（最小清单）

| # | 缺口 | 现状 | 建议最小动作 | 优先级 |
|---|---|---|---|---|
| 1 | 构建期版本号未注入 | `Version = "dev"`（`buildinfo.go:36`），仓库**没有任何 git tag**，无 Makefile/CI | 加 `Makefile`：`-ldflags "-X treecmd/internal/buildinfo.Version=$(git describe --tags --always --dirty)"`；发布流程 = 打 tag 后构建，并把 `Version` 与 `hash` 一起记入发布记录 | P1 |

## 6. ADR 草案

> 编号说明：现有《架构方案》§13 的 ADR 只写到 **ADR-023**，而代码注释里已经引用到 **ADR-051** ——
> 中间这批 ADR 未在架构方案里沉淀。本次新增建议直接从 **ADR-052** 起编号，
> 但在评审时需**确认 ADR-024~051 的归档位置**（是否要一并补写进 §13）。

### ADR-052：失效节点由显式运维命令清理，不做自动删除

- **Context**：父端关于子节点的记录散落在内存注册表、`state.dat.known_children`、以及 bbolt 的四个桶里；
  断连与驱逐都不删这些记录，`Table.Remove` 甚至没有生产调用点（`registry.go:132-136`）。
  误启动的实例、注册被拒但调过一元 RPC 的节点（`hub.go:268`）会留下永久残骸，
  并把 `/v1/tree`、健康聚合长期污染成"有一个不掉线的坏节点"。
- **Decision**：
  1. 新增显式命令 `GET/POST /v1/forget`（CLI 薄封装），由运维在**直接父**上执行；
  2. **在线子一律拒绝**，默认只清 `garbage`（从未 `Confirmed` 的残留），清长期离线真子需显式 `mode=stale`；
  3. 清理在**单条 bbolt 写事务**里完成，未终态 assignment 先收敛为 `CANCELLED` 再删；
  4. 事务成功后再 `Reg.Remove` + `saveState()`，打断"注册表 ↔ `known_children`"的自锁定闭环；
  5. **不做**"掉线即自动删除"—— 会误伤滚动重启中的正常节点，且丢失运维信息。
- **Consequences**：✅ 残留可回收、cmdlog 水位解锁、健康聚合恢复真实；
  ❌ 需要人工介入（可脚本化，遍历各节点 API）；`child_reports` 的全桶扫描是唯一性能代价（默认不删它）。

### ADR-053：版本一致性以"可执行文件哈希"为唯一判据，构建期版本号只做展示

- **Context**：系统已实现"连上即比对哈希、不一致即自同步 + 原地重启"（README「可执行文件一致性」），
  且代码注释已确立"**版本号不参与判定**"的原则（`buildinfo.go:12`）。
  但构建期版本号一直停留在 `dev`、无 git tag、无 `--version`，且没有"全树是否已收敛"的显式判定。
- **Decision**：
  1. **判据不变**：全树一致 = 所有节点 `build_hash` 相等；版本号字符串永不参与任何判定；
  2. 补齐可追溯性：构建注入 `git describe` 到 `buildinfo.Version`，新增 `-version`；
  3. 新增只读的**全树收敛判定**（`/v1/tree?converged=1`），供运维/CI 断言"版本已唯一";
  4. **不引入**注册期的哈希硬约束（`require_match`），保持"自同步收敛 + 巡检兜底"，避免在多父/无父等场景误拒。
- **Consequences**：✅ 版本可追溯、收敛可断言、不破坏既有链路；
  ❌ "版本唯一"仍是**涌现结果**而非强制不变量 —— 不收敛的窗口期（升级过程中）靠巡检发现。
