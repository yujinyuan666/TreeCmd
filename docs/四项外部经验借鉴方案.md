### 为什么 §2 永久不做

> **决定人原话：我的程序每个节点只对他的父节点负责。**

这条不是"暂缓"，是**架构前提的确认**：treecmd 的每个节点只与自己的父建立连接、只对自己的父
负责。于是"从任意一处到达任意节点"这件事**根本不该存在于这个系统里** —— 想操作一个孙节点，
就该由它的父去做，而那件事**本来就是父的职责**。

顺带说明：§2 里唯一有点独立价值的那半（`GET /v1/routes` 可观测 + 启动期拓扑自检）也一并放弃 ——
`parents[]` 是手工声明的人写配置，写错在启动强校验与注册环检测上就会暴露，不需要再引入一层
"路由视图"去解释它。

**后果**：`/v1/forget`、`/v1/crl`、`/v1/commands/{id}/retry` 的语义**就是"只对本节点名下生效"**，
不是缺陷。文档里要维持这个口径，别写"可以指定任意后代节点"。

## 1. 背压与自适应窗口（借鉴 taktuk 的 work-stealing + arity）

### 1.1 借鉴什么 / 不借鉴什么

| taktuk 的做法 | 本方案 | 原因 |
|---|---|---|
| **arity**：树的分叉度可调 | ⚠️ **不能直接搬** —— treecmd 的 arity = 直接子数，由部署决定、运行期不可改 | 改成"可调分叉"要动拓扑，等于换树 |
| **滑动窗口 / 有限并发推进** | ✅ **这是核心借鉴** | 现在下发侧只有字节上限，没有"同时在途条数"上限 |
| **`-d` 动态 work-stealing**：不让谁空转、不让谁过载 | ✅ **只借用它的"效果"** —— 窗口随在线子数自适应 | 见下一条 |
| work-stealing 本身：一个任务能被任意节点领走 | ❌ **不采纳** | treecmd 语义是"整棵子树**人人各执行一次**"，任务**不可再分配**。硬搬会破坏背书链（`HopChain` 绑 `ChildId`，`submit.go:352`）与聚合计数（`subtreeCount` 按子树累加） |

**一句话**：taktuk 的 work-stealing 想达到的效果是"负载均衡"，在 treecmd 里对应的**唯一合法形式**是**自适应在途窗口**，不是任务再分配。

### 1.2 现状缺口（精确）

`buildFetchResponse` 遍历该子的所有 Assignment，只要没终态、不在退避中就派生投递，**唯一的刹车是字节上限**（`delivery.go:399`）。

```
for _, cmdID := range tx.CommandIDsOfChild(childID) {     // delivery.go:360
    ...
    sz := int64(proto.Size(d))
    if used+sz > maxBytes && count > 0 { break }           // :399 —— 唯一刹车
    ...
    a.Status = LEASED
}
```

后果：**一个子可以一次把该指令下所有分派全拉走**。父端不知道"我已经给了这个子多少没回终态的东西"。`LocalBusy` 是**逐条、事后**的（子已经在跑了才拒），在此之前父已经把一批标成 LEASED 发出去了。

### 1.3 设计

**三件事，按收益排序：**

**(1) per-child 在途窗口（核心）**
父在 `buildFetchResponse` 里，**先数该子的非终态 Assignment 数**，只放行到窗口上限。

> **关键性质（决定了默认值可以安全取 8）**：窗口是**跨指令**的。单条指令对每个子只有 **1** 个 Assignment（`EnsureCreated` 里每子一条，`delivery.go:51-63`）。所以默认窗口 8 **对"单条指令"完全无影响**，只在"同一子同时积压 >8 条指令"时才生效。

**(2) 全局在途窗口**
父端"已 LEASED 且未终态"的总数上限，防止一个有 1000 个直接子的节点被自己的 fan-out 打爆。

**(3) 自适应 + 指数退避**
- `dispatch_window_adaptive=true` 时：`per-child 窗口 = max(1, total窗口 / 在线子数)`（`childOnline()` 已有）。
  这就是 taktuk `-d` 的效果等价物：**子在线的多 → 每子窗口收窄；子掉线了 → 剩下的子窗口放宽**。
- `LocalBusy` 退避从固定 3s 改**指数**：复用已有的 `BackoffUntil` 字段，新增 `AssignmentRecord.local_busy_streak`（**编号 18**）记连续 busy 次数，退避 = `min(local_busy_backoff << (streak-1), local_busy_backoff_max)`（落地时基数直接复用了已有的
  `local_busy_backoff`，没有再新造一个 `backoff_base` 字段 —— 见 §1.8 的差异表）。
  `LocalBusy` 的语义不变（**不推进 attempt**，`hub.go:840`），只是退避时长会增长。

### 1.5 兼容与迁移

- 全部默认值**不改变现有小规模行为**（默认 8 只影响"同一子积压 >8 条指令"）。
- 若想"零行为变更"，把两个窗口设 0。
- **父可热下发**（在 `command.` 白名单里）⇒ 不用改文件、不用 SIGHUP，`ConfigPush` 就能调参。这是本项最舒服的地方。

### 1.6 风险

| 风险 | 缓解 |
|---|---|
| **窗口与租约回收抖动**：回收把 LEASED→PENDING，在途数下降，下一轮又放行 → 反复投递 | 回收时给该 Assignment 设一个短 `BackoffUntil`（复用字段），避免同一轮内立刻重投 |
| 窗口过小拖慢吞吐 | 默认 8 且"单条指令不受影响"；文档给出"按 `children_count × 窗口 ≤ max_dispatch_inflight` 配"的经验规则 |
| 与 §4 的供片并发放大 | 两处共用同一套"窗口 + 信号量"写法，参数集中在 `command.` 与 `selfupdate.`，文档里交叉引用 |

### 1.7 验收（`test/backpressure.sh`）

1. 起 3 层树（复用 `demo.sh` 的材料生成）；
2. 一次提交 20 条 `sleep`（payload 各不同），`aggregate=TREE`；
3. **断言**：轮询 `/metrics` 的 `child_dispatch_inflight`，任何时刻 ≤ 配置窗口；
4. **断言**：最终 20 条全部 `COMMAND_STATUS_COMPLETED`（窗口只限速、不丢任务）；
5. 把窗口设为 0 重跑，断言行为回到"一次全拉走"（对照组）。

### 1.8 实际落地差异（2026-09-16）

设计与实现基本一致，有 **4 处刻意的偏离**，都记在这里，免得以后有人以为是漏做：

| # | 设计里怎么写的 | 实际怎么做的 | 为什么改 |
|---|---|---|---|
| 1 | 超窗口时 `continue`（"后面的指令可能已终态，不该被前一条挡住"） | **`break`** | 那条理由对**按字节**的刹车成立（后面的"小"指令确实还塞得进去），对**计数**窗口不成立：两个计数在循环内只增不减，一旦打满，后面任何一条都不可能再放行。`break` 与 `continue` 等价，但省掉整段白扫 |
| 2 | 新增 `command.backoff_base`（默认 3s）当退避基数 | **复用已有的 `command.local_busy_backoff`** 当基数，只新增 `local_busy_backoff_max`（默认 60s） | 两个字段名指同一件事（退避基数）必然让运维搞混，而这个参数本来就已经存在、已经在 `command.` 热更白名单里 |
| 3 | `max_dispatch_inflight` 默认 256 | **默认 0 = 不限** | 固定数字总会在某个扇出规模上开始咬人：单子窗口 8 时，只要直接子超过 32 个，全局 256 就会顶住，把本来能并行的下发变成一波一波。它想防的是"病态扇出"这种少见情况，所以默认关掉、按 `总数 ≥ 单子窗口 × 直接子数` 开 |
| 4 | 窗口字段是普通 `int32`，0 = 不限 | 改成 **`*int32`**（没配 = 默认值，显式 0 = 不限） | 本仓库现有约定是"0 即未配置"，两者冲突：运维写 `max_dispatch_inflight_per_child: 0` 想表达"不限"，却会被默认值顶成 8。用指针区分"没配"与"显式 0"，与 `selfupdate.piece_store` 的 `*bool` 是同一套写法 |

**另外两处值得记的实现细节**：

- **"在途"的定义**（`delivery.go` 的 `countInflight`）只说一件事：**LEASED 且租约仍有效**。
  `PENDING`（含被 `LocalBusy` 退回、正在退避的）不算；**`LEASED` 但租约已过期的僵尸租约也不算** ——
  后者是必须写下来的：父重启之后，旧租约在 `LeaseTTL`(90s) 内还没到期，如果把它们算进窗口，
  窗口会被一批永远不会回来的租约占满，节点在那一分半钟里**自己把自己锁死**。
- **指标标签用完整 NodeID，不用前 8 位**（`child_dispatch_inflight{child="<完整 ID>"}`）。
  NodeID 是 UUIDv7（时间有序），前 8 位就是毫秒时间戳 —— 同一秒启动的两个子前缀完全相同，
  拿前缀当标签会把两个子静默合并成一条曲线。这个坑本仓库已经踩过一次（片存目录名那次）。

**验收实测**（`test/backpressure.sh`，2 个直接子 × 20 条 `sleep 2.5s`）：

```
① 峰值在途 8 ≤ 窗口 8          （逐子分别取峰值：两个子都是 8）
② 20 条全部 COMMAND_STATUS_COMPLETED
③ 窗口热更成 0 后峰值在途 20 > 8，对照组成立；同样全部终态
```

**验收过程中顺带修掉的一个真问题**（不在本项计划内，是脚本先撞上的）：

`fetchLoop` / `heartbeatLoop` 原先用 `time.NewTicker(u.n.C().Command.RenewAt)` —— **周期在会话建立
那一刻就被快照了**，于是 HUP 改 `renew_at` 对已建立的会话完全无效，而 `examples/node.yaml` 承诺
`command.` 段「SIGHUP 重读即生效」。表现是验收脚本把 `renew_at` 从 30s 热更到 2s 之后，
子节点仍按 30s 的旧节奏拉取，阶段 A 白等 62s（时间线实测：轮次间隔 10.3s / 22.4s，
两次都落在同一个 30s 网格上，即"等旧周期走完"）。

修法：两个循环都改成 `renewAtStep`(1s) 小步长 + 每步现读 `u.renewAt()`（新增）。
**默认 30s 周期下的行为与 Ticker 完全一致**，但热更立刻生效 —— 阶段 A 因此从 62s 降到 19s。
这件事对本项尤其要紧：父只在提交那一刻通知一次，之后剩下的分派全靠子下一次轮询才拿得到，
所以"窗口限速时的轮次间隔"就等于 `renew_at`。

第 ③ 步是对照组，也是**唯一能证明"① 的上限来自窗口"的实验**：不限窗口时峰值从 8 跳到 20，
说明那个 8 不是"任务本来就快、天然堆不起来"的巧合。它同时顺带验证了新字段的 SIGHUP 热更通路
（`Reload()` 走整份 `config.Load`，不受 `allowedHotKey` 白名单限制；`command.*` 不进 `config_hash`，
所以不会触发重注册）。

## 2. 通用逐跳路由与拓扑自检（借鉴 ClusterShell 的 `topology.conf`）

### 2.1 关键结论：不要搬 `topology.conf`

ClusterShell 的 `[routes]` 解决的问题是：**"从一个 head 出发，为了到达某组节点，必须经由哪些 gateway"**（例：`rio0: rio[10-13]`、`rio[10-11]: rio[100-240]`）。

**treecmd 已经把这件事解决掉了**，而且更简单：每个节点**只连自己的父**，父地址写在 `parents[].addr`（`config.go:96`），路径由父在 `RegisterAck.path` 里下发（`registry.go:80`），祖先链由父下发（`upstream.go:266`）。也就是说 **"经谁到达"这条信息是内生的、逐节点自洽的**。

再引入一份中心化的 `routes:` 段会：
- 与 `parents[]` **信息重复**（两处声明同一件事，必然漂移）；
- 与"**薄**"的取向冲突 —— 用户此前明确否掉过给框架加配置段（见 `internal/exec/apis` 那轮的取舍）。

> **所以本节的借鉴点是 ClusterShell 的"精神"，不是它的配置格式**：把已有的拓扑信息变成**可查询、可路由、可自检**的能力。

### 2.2 真正缺的是什么（精确）

| 已有 | 缺 |
|---|---|
| 祖先链（`AncestorIds`）用于**环检测**与 health 白名单 | **没有一个通用的"路径/NodeID → 下一跳"解析**。`routeTable`（`query.go:105`）**只服务结果查询** |
| 健康检查是**唯一的通用逐跳转发**（`health.go:177-215`，父向子转发 `HealthReq`） | 其余端点**只能操作本节点 / 直接子**：`/v1/forget?node=`（`api.go:277`，`forget.go:10-21` 明确"本节点名下"）、`/v1/crl`（`api.go:240`，只写本地 + 推直接子）、`retry?node=`（`api.go:176-186`，只重跑直接子） |

**痛点具象化**：想把一个**孙节点**从树上清掉（`/v1/forget`），今天必须**先手工登录中继**、在中继上调一次；想从根吊销一个孙节点的证书，CRL 虽然会沿树下发，但"吊销"这个动作只能对直接子发起。

### 2.3 设计

**(1) 把 `routeTable` 泛化为通用下一跳解析**

新增 `internal/node/route.go`：

```
resolveNextHop(target string) (kind, nodeID string, err error)
// kind ∈ {local, child, unreachable}
// target 可以是 NodeID 或绝对路径 "/a/b"
// 1) target == 本节点 ID 或 == 本节点 path      → local
// 2) registry 里有这个 NodeID                    → child
// 3) 按【最长路径前缀】在直接子里选一个：用每个子的 Path + registry.Remaining/FirstSegment
//    （registry.go:311/331 已有工具，无需新写字符串处理）
// 4) 都不命中 → unreachable（附 hint：我视野里只有这些前缀）
```

复用现有 `routeTable`（`query.go:105-130`）做**解析结果缓存**（TTL = `query.query_route_ttl`，容量 = `query.max_query_routes`），**不新增配置**。

**(2) 通用逐跳转发层 —— 直接复用已有的 ReqAuth 委托凭证**

这是最省的设计：`auth.go` 里的 `ReqAuth` 已经是"入口签一次、逐跳原样透传、每跳离线验链 + 验 `ParamsHash`"（`verifyReqAuth`），而且**参数摘要只绑跨跳不变的量**（`reqAuthParams` 刻意排除 `depth`/`timeout`）。新增 `reqAuthKindRoute = 3` 即可：

- 每跳能用**预置的根证书**离线验出 `ViewerID` ⇒ 转发者身份可验证；
- `ParamsHash` 绑 `(target, action)` ⇒ 委托凭证**不能被挪用到别的目标**；
- `NotAfter` 给短 TTL（复用 `query.req_auth_ttl`）。

转发时每跳：
```
RouteReq{ target, action, payload, hop, budget }
  → 校验 ReqAuth（kind=3，ParamsHash 绑 target+action）
  → 校验 hop < query.max_route_hop（默认 16），budget 未过期
  → resolveNextHop(target)
      local  → 本地执行 action，回 RouteResp
      child  → 把 RouteReq 原样（hop+1、budget 递减）转给那个子
      other  → 拒（ERR_ROUTE_UNREACHABLE）
  → 每跳记审计日志（复用 auditReject 的风格）+ 把经过的节点拼进 RouteResp.via
```

**(3) 把三个已有端点接上目标路由**（这才是有价值的部分）

| 端点 | 目标语义 | 路由规则 |
|---|---|---|
| `GET /v1/forget?node=<任意后代>` | 预览 | 路由到**该节点的直接父**（forget 的权威在父端记录上） |
| `POST /v1/forget?node=<任意后代>` | 执行清理 | 同上 |
| `POST /v1/commands/{id}/retry?node=<任意后代>` | 重跑 | 同上 |
| `POST /v1/crl?node=<任意后代>` | 吊销 | **从根发起**才有意义（CRL 是沿树下发的）；路由用于"让驳回动作能命中孙" |

**(4) 拓扑自检（ClusterShell "可声明、可校验"的精神）**

- **新端点 `GET /v1/routes`**（只读）：本节点视角的路由表 —— 每个直接子 + 它名下的前缀、以及"经它可达"的说明。让运维**一眼看出"加一个节点后谁能到谁"**。
- **启动期静态自检**（符合本项目"启动强校验就在启动路径上"的风格，`README` 第 183 行那一段）：
  - 多父且两个父**声称的 path 不同** ⇒ 启动 WARN（说明这次会挂到不同位置，重启后 `SelfPath` 会变）；
  - `parents[].id` 为空或与证书身份相同（自己挂自己）⇒ 启动 **报错退出**（`nodes.json` 里已有环检测在注册时拒，这里把"配置期就能查出来的"前移）。

### 2.4 改动清单

**proto**

```protobuf
message RouteReq {
  string target  = 1;   // NodeID 或绝对路径
  string action  = 2;   // "forget.preview" | "forget.apply" | "cert.retry" | "crl.revoke"
  bytes  payload = 3;   // action 的参数（JSON）
  uint32 hop     = 4;   // 已转发的跳数，入口置 0
  google.protobuf.Timestamp budget = 5;  // 本跳整体截止（逐跳只减不增）
  ReqAuth req_auth = 6; // 复用已有委托凭证（kind = 3）
}
message RouteResp {
  bool   ok      = 1;
  string reason  = 2;
  bytes  payload = 3;
  repeated string via = 4;  // 实际经过的路径，便于排错
}
```
- `UpFrame` **18** = `RouteReq route_req`；`DownFrame` **16** = `RouteResp route_resp`
- `internal/node/auth.go`：`reqAuthKindRoute uint32 = 3`；`checkRouteReqAuth`（照 `checkQueryReqAuth` 写）

**代码**

| 文件 | 改动 |
|---|---|
| `internal/node/route.go`（新） | `resolveNextHop`、`RouteReq` 收发、hop/budget 递减、`via` 累积 |
| `internal/node/upstream.go` | `dispatch` 加 `RouteResp` 分支 |
| `internal/node/hub.go` | 下行 `RouteReq` 分支：本节点判定 → 本地执行或转给子；新增 `Hub.sendRouteReq(cc, req)` |
| `internal/node/api.go` | 新增 `/v1/routes`；`handleForget` / `handleCRL` / `handleCommandByID` 的 retry 分支加"目标不在本节点 → 发起路由" |
| `internal/node/forget.go` | 抽出"执行 forget 并返回 plan"的纯函数，供本地与路由两条路径复用 |
| `internal/config/config.go` | `QuerySection` 加 `MaxRouteHop int32 yaml:"max_route_hop"`（默认 16）；`SecuritySection` 加 `RouteOperators []string yaml:"route_operators"`（默认空 = 只允许 root + 直接父） |
| 指标 | `route_total{result="ok\|unreachable\|denied\|hop_exceeded"}`、`route_hop_hist`（可选） |
| 文档 | README 的「HTTP API」小节补 `/v1/routes` 与三个端点的目标路由语义 |

### 2.5 兼容与迁移

- 完全向后兼容：目标在"本节点/直接子"时**走原路径**（`resolveNextHop` 返回 local/child，不产生任何帧），只有**跨层**目标才走路由。
- 旧版本节点收到 `RouteReq` 帧：gRPC oneof 未知字段会被忽略 → 表现为"没反应"。所以**必须**在 `RouteResp` 超时后返回明确错误（不要静默等到 HTTP 超时）。`query.req_auth_ttl` 已经是现成的超时源。
- 建议**自上而下启用**（根先升），因为路由是"从上层发起"的。

### 2.6 风险（这一项是四项里最需要克制的）

| 风险 | 说明与缓解 |
|---|---|
| **安全面扩大（硬前置）** | HTTP API **本身无鉴权**（入口无 mTLS，`makeReqAuth` 只能"以入口自身身份代表调用方"）。加了路由后，`forget` / `crl` 这类**破坏性操作的射程从"直接子"扩到"整棵子树"**。⇒ **必须先落地 `security.route_operators` 白名单**，否则是净安全退化。这是本项的**准入条件**，不是可选项 |
| **这是唯一"扩框架"的一项** | 与"薄"张力最大。建议**拆两批落**：<br>①**只读批**：`resolveNextHop` + `GET /v1/routes` + 启动自检（零新帧、零安全面变化）；<br>②**转发批**：`RouteReq/RouteResp` + 三个端点的目标路由 + `route_operators` |
| 放大/环路 | `hop` 上限 + `budget` 逐跳递减 + ReqAuth 的 `ParamsHash` 绑 target（防"用 A 的委托去干 B"）+ 每跳审计 |
| 路由缓存陈旧 | 用 `routeTable` 的 TTL（`query.query_route_ttl`）；命中不到就**退化为逐跳问**（不缓存的慢路径），不要直接失败 |

### 2.7 验收（`test/routes.sh`）

1. 起 3 层树（根 → relay → leaf2），确认 `AncestorIds` / `path` 符合预期；
2. `GET /v1/routes`（根）断言能看到 relay 与 leaf2 的前缀；
3. `GET /v1/forget?node=<leaf2>`（根）断言：返回 relay 上的 ForgetPlan，且 `via` 含 relay；
4. 负向：拿一个不属于本树的 NodeID，断言 `ERR_ROUTE_UNREACHABLE`（不是超时）；
5. 负向：把 `query.max_route_hop` 设为 1，断言第 2 跳被拒且 reason = hop 超限；
6. 负向：`security.route_operators` 设为不含根的列表，断言破坏性操作被拒（403 + `ERR_ROUTE_DENIED`）。

## 3. CA 证书在线轮换（借鉴 Nested SPIRE 的 intermediate CA 模型）

### 3.1 先澄清一件事：层级中间 CA **已经实现了**

方案里最容易搞错的地方，先说清：

```
identity/lifecycle.go:325  func (id *Identity) IssueForPubkeys(childNodeID, idPub, caPub)
  :337  idCert = issueCert(childNodeID, idPub, id.CACert, id.CAKey, isCA=false)   // 身份证书，30 天
  :342  CertChain = [idCert] + 父的完整 CAChain                                    // ← 多级链
  :352  caCert = issueCert(childNodeID+"-ca", caPub, id.CACert, id.CAKey, isCA=true) // CA 证书，10 年
  :356  CACertChain = [caCert] + 父的完整 CAChain
```

所以一棵 3 层树的链是：

```
叶子身份证书链 = [ leaf-cert(中继CA签), 中继CA证书, 根CA证书 ]
中继CA证书链   = [ 中继CA证书, 根CA证书 ]
```

`ValidateStartup`（`identity.go:777`）用 `id.Chain[1:]` 当 intermediates、`id.CAChain[1:]` 当 CA intermediates，各自验到信任锚（根）。**这跟 Nested SPIRE 的 "下游 server 从上游拿 intermediate signing cert，同一 trust domain 签发"是同一个模型**，而且 treecmd 多了"私钥永远不出本机"（`enroll.go` 只提交公钥）。

**所以本项不是"引入中间 CA"，而是补上 SPIRE 真正的收益：intermediate 的轮换能力。**

### 3.2 借鉴什么 / 不借鉴什么

| SPIRE 的机制 | 本方案 |
|---|---|
| **intermediate 可轮换、下游不用换 root bundle**（下游只信 root） | ✅ **核心借鉴**（见 3.3） |
| **上游挂了 intermediate 继续工作** | ✅ 已满足（CA 证书 10 年，父挂了中继仍能签子证书），**不新增工作** |
| 下游 server 的 intermediate **不能再签 intermediate**（purpose 收窄） | ⚠️ 可选加固项，见 3.4 |
| SVID 1h / 半生命期轮换 / `availability_target` | ❌ **不借鉴**：treecmd 的 30 天 + 2/3 轮换 + 7 天宽限（`identity.go:911` `renewalGrace`）在"父停机自治"上**比 SPIRE 更强**，缩短只增加签发负载 |
| CA **密钥**轮换 | ❌ 不在本方案内，见 3.6 |

### 3.3 设计

**(3A) 中继的 CA 证书向父续签 —— 复用已有的续签帧**

现在已经有 `UpFrame.cert_renew_req`(15) / `DownFrame.cert_renew_offer`(14) 这对帧，用来给**身份证书**续签。**加字段就够，不新增帧**：

```protobuf
message CertRenewReq {
  string reason   = 1;
  bool   want_ca  = 2;   // 新增：true 表示"顺带把我的 CA 证书也续一下"
}
message CertRenewOffer {
  bytes  cert_chain    = 1;  // 身份证书链（不变）
  string reason        = 2;
  bytes  ca_cert_chain = 3;  // 新增：CA 证书链；空 = 本次不带
}
```

- **父端**：`maybeOfferRenew`（`node/lifecycle.go:59` 附近）扩展 —— 除了判 `id.Cert` 是否进窗口，**也判该子的 CA 证书**（父端有这个信息吗？见下"数据来源"），进窗口就一起重签并带上 `ca_cert_chain`。
- **新增 `identity.ReissueCAFor(existing *x509.Certificate, owner *Identity) ([]byte, error)`**：与 `ReissueFor`（`identity.go:624`）**唯一区别**是把 `:633` 那个硬编码的 `isCA=false` 改成 `true`。建议顺手把 `ReissueFor` 重构成调一个私有 `reissueWith(existing, owner, isCA bool)`，两处共用。
- **子端**：收到 `ca_cert_chain` →
  1. `identity.WriteCertChainFile(cfg.Security.CACertPath, chain)` 原子写盘（`enroll.go:403-407` 已有同款写法）；
  2. 热替换内存：`id.CACert` / `id.CAChain`；
  3. `n.refreshReloadBaseline()`（`enroll.go:412`）—— 否则这次改动会被 reload 监视当成"外部变更"或漏检。
- **`roots` 池不动**：本节点信任锚是**父/根**，不是自己。

> **数据来源问题（必须解决）**：父端现在**不知道**子的 CA 证书到期时间（注册请求里只有 `node_id` / `pubkey` / `build_hash`）。两个选项：
> - **A（推荐，薄）**：由**子端**判定。子自己持有 `id.CACert`，进窗口就发 `CertRenewReq{want_ca:true}`。父端只需在收到时"用本节点 CA 重签它的 CA 公钥" —— 但父**必须拿到子的 CA 公钥**。所以请求里得带 `bytes ca_pubkey = 3`（+ 可选 PoP 签名）。
> - **B**：`RegisterRequest` 加 `ca_not_after` 字段，父端统一调度。改动更大、要动注册。
>
> 采用 **A**：改动最小，且与"父不信任子自报进度"的既有风格一致 —— **父不认子的时间判断，只负责"你要我就签"**，签发本身仍受 `CA 私钥 + 子身份已注册` 两道约束。

**(3B) 根的 CA 证书自签续期**

`canSelfRenew()`（`node/lifecycle.go:271`）= "无父 + 有 CA 材料"，判据不用改。把动作从"只重签 `id.Cert`"扩展成两步：

1. **先** 用自身 CA 重签**自己的 CA 证书**（`ReissueCAFor(id.CACert, id)`，同一把 CA 私钥、同一公钥、同一 CN）→ 写 `certs/ca.crt` / `certs/node.crt.ca`；
2. **再** 用**新的 CA 证书**重签自己的身份证书 → 写 `certs/node.crt`。

> ❗ **顺序不能反**：反了会出现"身份证书链里引用的是旧 CA 证书"，虽然仍能验通，但链与磁盘上的 CA 证书不一致，重启后 `ValidateStartup` 的 `id.Chain[1:]` 校验会绕远路（能过但脆弱）。

**(3C) CA 证书生命期可配置（默认值不变）**

现在硬编码在 `identity.go:583-585`（30d / 10y）。新增：

| 字段 | 默认 | 说明 |
|---|---|---|
| `security.ca_cert_days` | **3650**（= 现状 10 年） | CA 证书生命期。**默认值刻意不变**，避免存量节点的 CA 证书"突然集体进续签窗口" |
| `security.identity_cert_days` | **30**（= 现状） | 身份证书生命期，同样只为对齐 `identity.go:583` |
| `security.renew_ratio` | 2/3 | 进窗口的判据（现在散在 `needRenew` 里） |

> 这三项**不进 `config_hash`**（`ConfigHash()` 是按字段白名单算的，天然不含 `security.ca_cert_days`）。**但要写进 `examples/node.yaml` 并明确标注"不进 hash"**。

**(3D) 可观测**

- `/v1/tree` 每个 child 加 `ca_not_after_days`；
- `/metrics` 新增 `ca_cert_not_after_days`（已有 `cert_not_after_days` 管身份证书）；
- 指标 `ca_rotate_total{result="issued|installed|failed|skipped"}`。

### 3.4 （可选加固）给 CA 证书加 `pathLenConstraint`

看 `issueCert`（`identity.go:570`）的 `isCA=true` 分支：现在**没有**设 `MaxPathLen` / `MaxPathLenZero`。也就是说**中继的 CA 在密码学上可以无限往下签**（可以签出"另一个中继的 CA"，一层层无限深），虽然业务上只有 `HasDownstream` 的节点才提交 CA 公钥。

可以借鉴 SPIRE "下游 server 的 intermediate 不能再签 intermediate"：

- 方案：`issueCert` 在 `isCA=true` 时设 `MaxPathLen = 1, MaxPathLenZero = false`（表示"这张 CA 证书只能再签一层 → 它只能签叶子的身份证书，不能再签 CA 证书"）。
- **但**：treecmd 的孙**也可能是中继**（需要自己的 CA 证书） ⇒ 一刀切会打断多层中继。
- **折中**：`security.ca_path_len`（默认 `-1` = 不限制 = 现状）。要收紧的部署自己设 1/2。**列为可选，不进第一批。**

### 3.6 兼容与迁移，以及**没有解决的那一半**

**为什么轮换 CA 证书不需要重分发 `trust/`（方案的立足点，实施者必须理解）**

`trust/` 里放的是**信任锚**。验证一条链的规则是"**链能接到某个信任锚**"。轮换时：

> 口径更新（信任锚自举落地后）：锚的"标准形态"是**你的父**的 `certs/node.crt.ca`（整份文件，
> 含父 CA 一路到根），而不是根 CA 证书；并且入网成功后锚可以由**本节点自己的证书链**自举出来
> （`identity.ChainAnchors`，`trust/` 可以删）。下面这段论证**不受影响** —— 它只依赖
> "锚是某张 CA 证书、且只看链不看锚的有效期"，与那张证书是根的还是父的无关。

- **轮换的是证书，不是密钥** ⇒ 新 CA 证书的公钥与旧的一模一样；
- 已入网子手里的链里含**旧的中继 CA 证书** ⇒ 旧证书在自己有效期内**依然有效**，链依然验得通；
- 新入网的子拿到**新的中继 CA 证书** ⇒ 一样验得通（因为它的签发者公钥没变）；
- 子用 `trust/` 里的**旧根证书**当锚去验"新签发的 CA 证书" ⇒ **验签结果相同**（公钥没变），而且 Go/Python 的 x509 实现**只检查链中证书的有效期，不检查 trust anchor 的有效期**（锚是被 trust-as-is 的）。

⇒ **结论：CA 证书轮换 = 在线完成、不重启、不重新入网、不动 `trust/`。** 这就是本项的全部收益。

**明确没有解决的（不要含糊）**：**CA 私钥轮换**才是真的"换 CA"，那必须全树重分发 `trust/`。本方案**不解决**它。第二阶段轮廓（供参考，不在本次范围）：

1. 生成新 CA 密钥对；
2. `ca_cert_paths` 里**同时放新旧两张根证书**（信任锚双活）；
3. `ca_key_path` 指向新密钥，用新 CA 重签所有子的链；
4. 等所有子的 `trust/` 都换完之后，再撤掉旧锚。

第 2 步是关键：**信任锚双活**让"换密钥"变成一个可以慢慢推进的过程，而不是一次全树停机。

### 3.7 风险

| 风险 | 缓解 |
|---|---|
| 续签时必须沿用 `"<nodeID>-ca"` 命名约定，否则 `ValidateStartup` 的 CN 检查（`identity.go:839`）会让**中继下次启动直接失败** | 实施注意里写死；验收里加"续签后重启中继"这条断言 |
| 根"先续 CA、再续身份"的顺序被写反 | 在 `resignSelfCert` 里加注释与断言（新 CA 证书的 `Raw` 必须出现在新身份链的 `Chain[1]`） |
| 缩短 `ca_cert_days` 会让存量节点突然进窗口 | **默认值保持 3650**；文档显式提示"改小之前先确认树里所有中继都能连上父" |
| 中继与父断联期间恰好在续签窗口 → 续不上 | 中继的 CA 证书在有效期内仍可用 ⇒ **不会停机**；断了就下次重连再续（`CertRenewReq` 是幂等的：同一公钥重签） |

### 3.8 验收（`test/ca-rotate.sh`）

1. 起 3 层树；把 `security.ca_cert_days` 设成很短的值（例如 1），让中继的 CA 证书立刻进窗口；
2. **断言**：中继日志出现 `ca renew`，且 `certs/node.crt.ca` 的指纹**变化**；
3. **断言（关键）**：叶子 `trust/root-ca.crt` **未变**，且叶子↔中继的 mTLS **仍通**、指令仍能下发成功；
4. **断言**：重启中继，`ValidateStartup` 通过（验证 CN 约定与"先 CA 后身份"的顺序）；
5. **断言**：让一个新叶子 `-enroll` 到中继上，拿到的是**新 CA 证书**链，且它只信任旧根就能验通。

### 3.9 实际落地差异（实施后回填）

实施时对上面的设计做了三处调整，都是**变得更简单/更严**：

**① 请求里带的是"当前那张 CA 证书"，不是 CA 公钥。**

原设计写的是 `bytes ca_pubkey = 3`。实施时发现：**公钥本身证明不了任何事** ——
父需要一个能证明"要续的是同一把密钥"的凭据，而"同一把密钥"这个判断必须有一个**参照物**。
所以改成 `bytes ca_cert = 3`（子当前那张 CA 叶子证书的 DER），父据此做四道校验
（能解析 / IsCA+certSign / CN 含该子 ID / 能验到本节点的信任锚），再沿用它派生出的公钥签发。
见 `reissueChildCA`。

**② `security.renew_ratio` 没做。**

判断：2/3 是既有约定（`renewWindowNumerator`），改它没有明确需求；而 `needRenew` 有 5 处调用点，
为它加一层配置的改动面大于收益。**只做了 `ca_cert_days` 与 `identity_cert_days`**，
且默认值 = 历史行为（3650 / 30），所以**零行为变更**。

**③ `issueCert` 的 CA 分支补了 `KeyUsageCRLSign`。**

原来只有 `GenerateRoot` 直接手搓的那张根 CA 证书带 `CRLSign`，走 `issueCert` 的中继 CA 证书没有。
轮换如果不补这一项，就会出现"轮换后的 CA 证书比原来少一项权限"这种难解释的差异。

**其余落地事实（与设计一致，列出来便于对照代码）**

| 项 | 落点 |
|---|---|
| 底层重签原语 | `identity.reissueWith(existing, owner, isCA)`；`ReissueFor` / `ReissueCAFor` 都是它的薄封装 |
| 子端判定与请求 | `requestCertRenew` / `caNeedsRenew` / `certsNeedRenew`（身份与 CA **一起判**） |
| 父端处理 | `handleCertRenewReq`（取代了 hub 里对 `maybeOfferRenew` 的直接调用 —— 不改的话"子只想换 CA、身份证书还很新"的请求会被静默丢弃） |
| 子端落地 | `applyCACertRenew`（三道校验，**不重建信任锚池、不触发重连**：TLS 上出示的是身份证书链，不含自己的 CA 证书） |
| 根的两步 | `reissueForSelf` 返回 `selfRenewResult{Chain, CAChain}`，`applySelfRenew` 先写 CA 再写身份 |
| 可观测 | `/v1/tree`：本节点 `cert_not_after_days` / `ca_not_after_days`；每个子 `ca_not_after_days`（**由子上报** —— 父手上只有子的身份证书）。指标 `ca_cert_not_after_days`、`ca_rotate_total{result}` |

> ⚠️ **父端 CA 证书剩余天数来自子上报，不持久化**：父重启后该项在子重连并重新注册之前会显示 0。
> 这是刻意取舍 —— 为它改 `state.dat` 格式不值得（那是可丢弃重建的状态文件，而 CA 天数每次注册都会刷新）。

### 3.10 实测抓到并修掉的两个产品级问题（**这是本节最值得读的部分**）

实施完跑端到端时，子节点开始报 `x509: certificate signed by unknown authority`，
两个问题**都不是本方案新引入的代码**，而是既有代码里被本方案"照出来"的盲区。

#### 问题 ①：`ChainVerifier` 对"同密钥锚"完全盲——而且那条兜底是死代码

`identity.ChainVerifier` 里的兜底逻辑（`chainTrusts`）**永远不会生效**，两重门：

```go
// 原代码
inters := x509.NewCertPool()                    // ← ① 裸池：poolSubjects 的旁路索引是空的
...
if _, err := leaf.Verify(...); err != nil {
    if grace > 0 && ... && chainTrusts(roots, inters, leaf) {   // ← ② 只认 grace>0
```

- **② 入网握手传的是 `grace = 0`**（`NewEnrollClientTLSConfig`），所以这条兜底在握手路径上
  **从来不会被执行**；
- **① 即使执行了也没用**：`chainTrusts` 的最后一段靠 `poolSubjects(inters)` 遍历中间证书，
  而它依赖 `identity.NewPool` 建立的旁路索引；裸 `x509.NewCertPool()` 下这个遍历是空的
  —— **那段"自签中间证书直接放行"的逻辑是死代码**。

**后果**：TLS 层只认"链末端的自签证书**逐字节等于**某个信任锚"。而 CA 证书轮换后链末端
必然是一张**新证书**（同密钥、不同 serial）⇒ 轮换一次，所有已入网节点全部连不上。

**修法**：把"链能不能接到锚"收成**唯一入口**，所有地方都走它。

```go
// internal/identity（现在全仓只有这一个判定入口）
func ChainToAnchor(chain []*x509.Certificate, anchors []*x509.Certificate, grace time.Duration) error
//   1. x509.Verify              —— 正常路径（含有效期与基本约束）
//   2. chainTrustsSameKey       —— 同密钥锚（CA 轮换形态），**仍要求链上证书未过期**
//   3. chainTrusts              —— 只认签名不看时间，仅 grace>0 时生效（续签宽限）
```

改用它的一共 5 处：`ValidateStartup`（**身份链与 CA 链各一次**）、`ChainVerifier`、
`applyCertRenew`、`applyCACertRenew`、`reissueChildCA`。同时把 `inters` 改用 `NewPool` 建
（让那段原本的死代码真正生效）。

> **教训**：`ValidateStartup` 里那段"CA 证书链要能验到信任锚"与 `ChainVerifier` 里的判定
> 是**同一件事的两个副本**。只在其中一处加特例，就会出现"TLS 能过、启动校验过不了"
> 这种自相矛盾的状态 —— 实测踩到过（日志只留一句"自签重签后的证书未通过强校验"）。

#### 问题 ②：重签**必须逐字节沿用**旧证书的 `RawSubject`

`issueCert` 原来是 `Subject: pkix.Name{CommonName: cn, Organization: []string{"treecmd"}}`
—— 重签时用同样的 CN/O **重建**一个 Subject。这**不等于**旧证书的 Subject：

x509 里"同名"是按 **`RawSubject` 的字节**判的，而**同一个逻辑名字由不同工具生成的 DER 并不相同**
（openssl 与 Go 的 RDN 顺序不一样）。`openssl x509 -subject` 会把顺序**归一化后打印**，
所以肉眼看两条 subject 一模一样，字节却不同 —— 于是重签出来的证书被判成"另一个 subject"，
`chainTrustsSameKey` 第 4 条（subject 相同）不成立，链断在那儿，
报错仍然是那句 `certificate signed by unknown authority`，而**公钥明明还是同一把**。

**修法**：`issueCert` 拆出 `issueCertWithSubject(cn, subjectDER, ...)`（`subjectDER` 非空时
Go 的 `CreateCertificate` 会直接用它当 Subject，不再重编码），`reissueWith` 把
`existing.RawSubject` 原样传进去。**只在"逐字节沿用"之后，"同名"才是真的同名。**

> 顺带一个实测观察：demo 里 `certs/ca.crt` 与 `certs/node.crt.ca` 是**两张不同的证书**
> （都由 `init_root.sh` 用 openssl 生成，同一个 key、不同 serial；信任锚分发用的是前者）。
> 所以"轮换 CA 证书"时真正要比的是 **RawSubject + 公钥**，不能指望"文件内容相等"。

#### 问题 ③（可观测缺口）：启动路径轮换 CA 证书时一行日志都没有

`renewSelfCert`（运行期）会打"CA 证书已轮换"，而**启动路径**（`loadIdentity` 里的自签续期）
也轮换 CA 证书，却没有任何出口 —— `loadIdentity` 是自由函数、拿不到 `Node` 来打日志。
修法：`identityBundle` 加 `caRotated []*x509.Certificate` 把结果带出来，
`NewWithPath` 调 `noteCARotated(st.caRotated)`；运行期那条也改成调同一个函数，
**两条路径的日志与指标从此一致**。

#### 验证方式（有正向也有负向）

`test/ca-rotate/main.go -selftest`：不算文件、不起进程，在内存里跑一遍完整机制并断言：

| 断言 | 内容 |
|---|---|
| A | 轮换后 CA **公钥逐字节不变**（这是"下级不用换 trust/"的依据） |
| B | 轮换后 CA 证书的 **`RawSubject` 逐字节不变**（问题②的回归） |
| C | **用旧的信任锚**能验通 `[新身份证书, 新 CA 证书]` 这条链（问题①的回归） |
| D | **负向**：同 subject、**不同密钥**的自签 CA 证书**必须被拒**（证明放行的是"同密钥"而不是"同名"） |

`test/ca-rotate.sh` 则是端到端的：把根的 CA 证书**做旧**（NotBefore 往前挪）使确定性地
落进续签窗口 → 重启根 → 断言日志、文件指纹、**信任锚文件未被改动**，以及"既有子节点
照旧在线、指令照旧跑完"。

## 4. 镜像分片的流水线分发（借鉴 Dragonfly 的 piece 级流式分发）

> ⚠️ **本节与其他三节不同：请先做 4.6 的测量，再决定做不做 4.2–4.4。**
> 4.1（manifest）无论测量结果如何都值得做。

### 4.1 借鉴什么 / 不借鉴什么

| Dragonfly 的做法 | 本方案 |
|---|---|
| **piece 级流式**："下载完一片就能立刻共享"，不等整份 | ✅ **核心借鉴** |
| **manifest 先行**（先给清单再给数据） | ✅ 借鉴（也是"片级可信"的前提） |
| P2P swarm / 跨层多源拉取 | ❌ **不采纳**（理由见 §6） |
| **按需 lazy-pull**（只拉用到的片） | ❌ **不适用**：treecmd 的镜像是**可执行文件**，必须完整才能 `exec` |

### 4.2 现状瓶颈（精确）

```
build.go:602  SameAsDisk(info)          // 供片前必须"磁盘文件 == 启动时那份"，否则 ERR_BINARY_LOCAL_CHANGED
build.go:640  顺序读自己磁盘 → 分片 → cc.sendThrottled 逐片推
build.go:406  chunk.Index != nextIndex || chunk.Offset != written → 直接失败（强顺序）
build.go:363  出错/超时 → os.Remove(tmp)，下次从 0 重来（无断点续传）
build.go:429  整份 sha256 只在【最后一片】才验
build.go:470  rename → build.go:520 syscall.Exec 原地重启
```

⇒ **收敛是逐层串行的**：根 → 中继（收完整份 + 校验 + rename + **重启**）→ 中继重启之后才可能给叶子供片。
总时间 ≈ **层数 × 单层时间**。

⚠️ 但请注意上界：`selfupdate.sync_timeout` 默认 60s、`max_bytes` 默认 64MB。所以单层最坏 60s、4 层最坏 240s；**如果实测单层是 1s，4 层也只有 4s，那 4.2–4.4 就不值得做**。这就是为什么本节要先测量。

### 4.3 设计

**(4.1) 片清单（manifest）先行** —— 无争议的底座

```protobuf
message BinaryManifest {
  string hash       = 1;   // 整份 sha256（与 RegisterAck.server_binary_hash 一致）
  int64  size       = 2;
  int64  chunk_size = 3;
  repeated bytes piece_sha256 = 4;  // 每片一个 sha256
}
```
- `UpFrame` **19** = `BinaryManifestReq binary_manifest_req`（子申请清单：`want_hash`）
- `DownFrame` **17** = `BinaryManifest binary_manifest`
- 收益：把"片级校验"从 crc32（**只查传输损坏**，proto 自己这么写的）升级为 **sha256（可查内容真伪）**。这是后面所有"边收边转发"的**前提**——否则中继会把未验证的片转发出去。

**(4.2) 片存 + 边收边转发（核心收益）**

- 片存位置：`<selfupdate.dir>/pieces/<hash 前 12 位>/<index>`（按目标哈希分目录，避免混）；上限 `selfupdate.piece_store_max_bytes`，超了 LRU 清。
- 子端收片流程改为：**先验片级 sha256**（crc32 保留作快速预检）→ **落片存** → 再写整份暂存文件。
- **`serveBinary` 增加一条路径**：若片存在于片存，**从片存供片，不再要求 `SameAsDisk`**。
  这就是"边收边转发"的落点：中继在**还没重启**、甚至**还没收完**时，就能把已收到的片转发给叶子。
  ⇒ 收敛从"逐层串行"变成"**流水线**"。

> 🔒 **安全硬约束（必须实现）**：片存只能对"**本节点 CA 签发的直接子**"开放（沿用 `canServeBinary`，`build.go:546`）；且**只能按 manifest 里的片号取片，绝不接受任意 offset 请求** —— 否则这就是一个任意文件读取漏洞。这一条要写进代码注释与 `docs/`。

**(4.3) 断点续传**

- `BinaryReq` 加 `int64 from_index = 3`（已有 1=`want_hash`、2=`max_bytes`）。
- 子端：重连/重启后扫片存，算出 `from_index`（**必须从片边界开始**，与现有 `chunk.Index/Offset` 强校验兼容）；
- 父端 `serveBinary` 从 `from_index` 起推。
- 因为片存按 hash 命名、跨 `exec` 存活，**这一条几乎是白送的**。

**(4.4) 收敛进度可观测**

- `/v1/tree` 加 `selfupdate_progress`（已收片/总片）；
- 指标 `selfupdate_pieces_received_total{result}`、`selfupdate_serve_pieces_total`。
- 这是验证"流水线真的跑起来了"的唯一手段（否则你只在最后看到 `lagging_children` 归零）。

**(4.5) 供片并发控制**

中继可能同时"拉父"和"推给 3 个孙"，必须限流：`selfupdate.max_serve_concurrency`（默认 4）。
**实现上直接复用 §1 的窗口/信号量写法**（`health.go:189` 那套 `sem := make(chan struct{}, fanout)`），不要另造一套。

**(4.6) 先测量再决定**（本节的准入条件）

新增 `test/selfupdate-timing.sh`（或给 `selfupdate.sh` 加 `timing` 子命令）：
1. 起 4 层树，用 `selfupdate.sh prepare` 造一个**明显更大**的镜像（例如 40MB）；
2. 记录每个节点"从收到第一个片到完成 exec"的时长，以及"从根开始替换到 `lagging_children=0`"的总时长；
3. **决策规则**：
   - 总时长 < 10s ⇒ **只做 4.1，不做 4.2–4.4**（收益不值得复杂度）；
   - 总时长 ≥ 10s 且瓶颈在"逐层串行等待"⇒ 做 4.2 + 4.3；
   - 瓶颈在带宽 ⇒ 做 4.5（并发/限速）而不是片存。

### 4.5 兼容与迁移

- **4.1 独立可落**：老节点收到 `BinaryManifest` 帧会忽略（oneof 未知字段）⇒ 子端要能**回退**：清单请求超时（例如 `sync_timeout` 的 1/3）就退回现有的 crc32 流程。**不要改成"没清单就不工作"。**
- **4.2/4.3 默认关闭还是开启？** 建议 `selfupdate.piece_store` 默认 **true 但只在"本节点有直接子"时才真正启用**（叶子开着没意义，也没有副作用）。
- 片存目录要在 `max_attempts` 防循环的逻辑之外**不影响判定**：`state.dat.self_update` 只记尝试计数，片存是可丢的缓存。**片存损坏 = 重拉，不是失败。**

### 4.6 风险

| 风险 | 缓解 |
|---|---|
| **复杂度显著上升** | 片存带来四个新问题：磁盘占用 / 清理 / 校验失败回滚 / 重启后一致性。所以 4.6 的测量是**准入条件** |
| 磁盘被打满 | `piece_store_max_bytes` + LRU；片存满了就"退化为只给自己用、不再供片"（fail-safe：不影响本节点自身的升级） |
| 把未验证的片转发出去（**最危险**） | 片级 sha256 必须**在落片存之前**校验；未通过校验的片**绝不入片存** |
| 任意文件读取 | 只按 manifest 片号取片；只对直接子开放；片存目录权限 0700 |
| 与 §1 的参数打架 | 供片并发用同一套窗口语义；文档里交叉引用，避免出现"两套限流各说各话" |
| 中继"半份镜像"被叶子拿去 exec | **不可能**：叶子仍然拿到完整清单，且最后一片才做整份 sha256（`build.go:429`，这条逻辑不动），只有全片齐 + 整份校验通过才 rename |

### 4.7 验收

1. `test/selfupdate-timing.sh`：给出 4.6 的测量数据与决策结论（**先跑这个**）；
2. 若做 4.1：断言子端日志出现 `piece verify ok (sha256)`；把某一片的字节改掉，断言**在片级就被挡住**（而不是等到最后一片才发现）；
3. 若做 4.2：断言叶子在"根→中继尚未完成"时**已经开始收片**（用 `selfupdate_pieces_received_total` 的时间戳比较）；
4. 若做 4.3：断言中断一次连接后，父端从 `from_index` 继续（日志里 `resume from piece N`），而不是从 0；
5. 负向：改坏片存里的一片，断言被丢弃并重拉，且**不影响本节点自身的升级成功**；
6. 负向：一个非直接子（拿不到本节点 CA 签发的证书）申请片，断言 `ERR_BINARY_NOT_DIRECT_CHILD`。

### 4.8 实际落地差异（实施后回填）

**做了的三处调整：**

**① 两条路径在代码里是显式分开的，不是"能拿清单就走新路"。**

`pullBinary` 里用 `useStore` 一个布尔贯穿到底：
拿到清单 → **每片先过 sha256 再落片存**，最后统一拼装；拿不到清单 → **与改造前逐字节一致**
（crc32 校验、直接追加进暂存文件、只有整份 sha256 兜底、不落片存、不支持续传）。
旧版父（不认识 `BinaryManifestReq` 帧）在 `fetchManifest` 的独立预算（1/3 同步预算，至少 5s）
超时后自然回退，**"拿不到清单就不工作"这种情况不存在**。

**② 供片时的片大小以"清单"为准，不以本地配置为准。**

`serveBinary` 里 `chunkSize` 的取值顺序是：清单里的 `chunk_size` → 本地 `selfupdate.chunk_size`。
原因：子存的那些片是按**清单**的片边界切出来的，两边口径不一致会导致"片号/偏移对不上"
或"拼装出来字节错位"。这也是清单里必须带 `chunk_size` 的原因。

**③ 断点续传的起点是"从第 0 片起的连续前缀"，不是"有几片"。**

`pieceStore.Prefix` 只算连续前缀 —— 中间缺一片的话后面那些片对拼装没用。
配套地，**最后统一拼装**（`Assemble`）而不是"边收边追加"：续传时前半段只存在于片存里，
暂存文件里没有，往里追加会得到一个内容错位的文件。统一拼装让"全新下载"与"续传"走同一段代码。

**④ 没有做 `selfupdate.serve_pieces_before_restart` 这个开关。**

判断：片存里只可能有**已通过 sha256 校验**的片，所以"能不能转发"本来就不取决于"收完没有"
—— 收完没有只决定"有几片可发"。多一个开关只会多一种状态，去掉。

**其余落地事实**

| 项 | 落点 |
|---|---|
| 片存 | `internal/node/pieces.go`：`<暂存目录>/pieces/<hash 前 12 位>/{manifest,piece-00000000}`，目录 0700 |
| 片存的三条安全边界 | ① 只有过 sha256 的片才入存；② 读取只接受**片号**（`Get(hash, index)`），绝不接受 offset；③ 按哈希分目录 |
| 清单的两个来源 | `Hub.manifestFor`：片存（继承自父 / 上次下载留下）→ **从本节点自己的镜像现算**（根节点就是这条） |
| 现算前的硬检查 | `buildinfo.SameAsDisk` —— 否则算出来的片哈希对应的是另一份内容，子会"每片都过、整份不过"，报错极难懂 |
| 供片来源 | 片存优先（**不需要 SameAsDisk**）→ 自己的可执行文件（必须 SameAsDisk，老路径） |
| 并发闸门 | `selfupdate.max_serve_concurrency`（默认 4）；满了**等到超时才拒**（`ERR_BINARY_BUSY`），不立刻拒 —— 子端一次失败要等下一轮重连才重试，太容易拖慢收敛 |
| 容量控制 | `selfupdate.piece_store_max_bytes`（默认 = `max_bytes` × 2），超了按最近使用时间清；清理失败绝不影响正在进行的同步 |
| 可观测 | `/v1/tree` 加 `piece_store`（每份镜像的 `have`/`total`/`bytes`/`ready`）；指标 `selfupdate_pieces_received_total{result}`、`selfupdate_serve_pieces_total{source}` |

## 5. 推荐落地顺序

按"收益 / 风险"排（**不是**按写作顺序）：

| 序 | 项 | 理由 |
|---|---|---|
| **1** | **§3 CA 证书在线轮换** | 收益明确（解掉"换 CA 要全树重分发 `trust/`"痛点）、改动小（**复用已有续签帧，零新帧**）、风险低、不碰分发主干。**当前写着"CA 证书不参与自动续期"的文档必须同步改** |
| **2** | **§1 背压与自适应窗口** | 有真实规模痛点、改动集中在一个函数 + 配置；且**父能热下发**（在 `command.` 白名单里），调参不用重启 |
| **3** | **§4.1 manifest** | 小改动、无争议、把片级校验从 crc32 升到 sha256。**4.2–4.4 先跑 4.6 的测量再决定** |
| **4** | **§2 通用逐跳路由** | 唯一"扩框架"的一项、与"薄"张力最大。**必须先落 `security.route_operators`**（准入条件），并拆"只读批 / 转发批"两步走 |

每项落地时都要走完整清单：`gofmt` / `build` / `vet`、`examples/node.yaml` 同步、README + docs 同步、新增接口同步 README 的「HTTP API」小节、`test/` 下加验收脚本。

## 6. 不采纳清单（附理由）

写在这里是为了**避免以后有人再把它们重新提出来**（每条都是本轮检索里真实存在的东西）。

| 借鉴物 | 不采纳的部分 | 理由 |
|---|---|---|
| taktuk | **work-stealing（任务再分配）** | treecmd 语义是"整棵子树**人人各执行一次**"，任务**不可再分配**。硬搬会同时破坏两处：`HopChain` 绑 `ChildId`（`submit.go:352`）与聚合计数（`subtreeCount` 按子树累加）。只取它想达到的**效果**（自适应窗口），已落 §1.3 |
| taktuk / pdsh | **可调的 arity（分叉度）** | treecmd 的 arity = 直接子数，由部署决定、运行期不可改；改成可调等于换树。能调的是"每轮推进窗口"，已在 §1 |
| ClusterShell | **`topology.conf` 这个配置段** | "经谁到达"已由 `parents[].addr` + 父下发的 `path`/`ancestor_ids` 完整表达；再加一份中心化 routes 段与它信息重复（必然漂移），且与"薄"的取向冲突。只取其"可声明、可自检"的精神 → `/v1/routes` + 启动自检（§2.3(4)） |
| ClusterShell | **多路径冗余 / 换父重挂** | treecmd 的多父是"**故障转移依次尝试**"（`enroll.go:275-282`），不是多路并存。改成"父挂了换另一个父重新挂载"会改变 `path` 与祖先链，与环检测、背书链、聚合三处都冲突。**明确不采纳** |
| Nested SPIRE | **SVID 短生命期（1h / 半生命期轮换）** | treecmd 的 30d + 2/3 轮换 + 7d 宽限（`identity.go:911`）在"**父停机自治**"上比 SPIRE 更强；缩短只增加签发负载与重连次数 |
| Nested SPIRE | **CA 密钥轮换** | 不在本方案内。CA **证书**轮换已由 §3 解决；密钥轮换才是"真换 CA"，需要全树重分发 `trust/`，轮廓见 §3.6 第二阶段（信任锚双活） |
| Dragonfly | **P2P swarm / 跨层多源拉取** | 需要 peer 发现 + 一套全新的"谁有资格供片"信任面，与"手工声明、薄"正面冲突；镜像是几十 MB 级（`selfupdate.max_bytes` 默认 64MB），收益不足以支撑。<br>**重新评估的触发条件**：镜像 > 100MB，或树层数 ≥ 4 且实测总时长 ≥ 10s |
| Dragonfly | **按需 lazy-pull** | 不适用：treecmd 的镜像是**可执行文件**，必须完整才能 `exec`；部分加载无意义 |
