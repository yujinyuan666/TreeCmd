## 一、这是什么：一句话与要解决的问题

**一句话**：treecmd 是一套**树形拓扑上的分布式指令执行与结果聚合框架** —— 一个进程同时扮演"服务端 + 客户端 + 执行引擎"三种角色，节点**自下而上注册成树**，指令**自上而下逐跳分发**并**就地执行**，结果**自下而上逐层聚合**，最终收敛到发起节点。

它解决的是这一类别的问题：

| 问题 | 传统做法 | treecmd 的做法 |
|---|---|---|
| 一次操作要覆盖一大片节点 | 中心化逐个下发，中心成为瓶颈与单点 | 指令沿树**逐跳扩散**，每个节点只与自己的直接父/子通信 |
| 需要"整片区域的汇总结论" | 各节点分别上报，中心再做一次全局聚合 | 结果**在树的每一跳就地聚合**，最终只有一份结论到达根 |
| 某个节点掉线/重启后状态不一致 | 依赖重试与最终一致，容易漏执行或重复执行 | **Assignment + 租约 + 本地三态 + child_reports 权威副本**：既不漏（对账补建）也不重（`SELF_DONE` 与终态绝不重跑） |
| 大结果传不回来 | 一刀切走对象存储或一刀切走消息 | **三级自动升降**：内联 ≤256KB / 分片 ≤64MB / 对象存储引用 >64MB |
| 谁都能问健康状况 | 无鉴权或仅靠网络隔离 | **每跳身份签名 + 四步校验 + `ReqAuth` 跨跳委托 + 逐跳白名单** |
| 证书过期导致全树失联 | 手工逐个换证 | **父在子生命期 2/3 处即时换发**，7 天宽限窗口内仍能握手换证 |

设计约束（决定了大量实现细节）：**不用外部中间件**（自建 Immich 式的"够用、干净、可控"风格）——没有 Redis、没有 etcd、没有消息队列；状态全在本机 bbolt + 本地文件；协调全靠父子直连的 gRPC 双向流。

## 二、系统全景与运行模型

### 2.1 一个进程 = 三种角色

```
                 ┌──────────────────────────────────────────────┐
   父节点 ──────►│  DownstreamHub（gRPC 服务端）                 │
                 │   · Connect 双向流：所有父→子控制帧           │
                 │   · FetchCommands / ReportResult / StreamResult│
                 │   · 拦截器：mTLS 身份 + CRL + 续签宽限         │
                 ├──────────────────────────────────────────────┤
                 │  TaskEngine（指令主干）                       │
                 │   handle → EnsureCreated → 本地执行 →         │
                 │   waitChildren → 聚合 → terminal → 上报       │
                 ├──────────────────────────────────────────────┤
   子节点 ◄──────│  UpstreamLink（gRPC 客户端）                  │
                 │   · 注册/RESUME、心跳续租、拉指令、报结果      │
                 │   · 重连退避 1s→30s + jitter                  │
                 └──────────────────────────────────────────────┘
                      bbolt 账本 + state.dat + objects/ 对象存储
```

三种角色在**同一进程内**运行，由 `node.yaml` 里的 `role`（推导自"有无父 / 有无子"）决定开启哪些：

| 形态 | 条件 | 上行侧 | 下行侧 | HTTP API |
|---|---|---|---|---|
| **root（根）** | 无父，有子 | 关 | 开（监听） | 开 |
| **relay（中继）** | 有父，有子 | 开 | 开（监听） | 可开 |
| **leaf（叶子）** | 有父，无子 | 开 | 关（不监听端口） | 关 |

> 5 层 × 3 子的实例：121 个节点里只有 **40 个**（根 + 中继）需要监听 TCP 端口，**81 个叶子不占端口** —— 这是"树形扩散"相比"扁平原厂"在部署上的直接收益。

### 2.2 三类数据流

| 方向 | 载体 | 内容 |
|---|---|---|
| **上行（子 → 父）** | `Connect` 双向流 | `Register` / `Resume` / `Heartbeat` / `LeaseRenew` / `Reconcile`（重连对账）/ `CRLReq` / `CertRenewReq` / `InflightHint` |
| **下行（父 → 子）** | 同一 `Connect` 流 | `RegisterAck` / `CommandNotify` / `CommandCanceled` / `TerminalNotice` / `HealthReq` / `QueryReq` / `RevocationList` / `CertRenewOffer` / `ConfigPush` / `HeartbeatAck` |
| **结果（子 → 父）** | `ReportResult`（一元）或 `StreamResult`（双向流分片） | `Report`：本地状态 + 聚合结果 + 子树背书链 |

> 关键设计：**控制面与数据面共用同一条 `Connect` 流做控制，结果单独走 `ReportResult` / `StreamResult`** —— 控制帧永远不被大结果阻塞。

### 2.3 节点状态机（三种粒度，互不混淆）

| 粒度 | 枚举 | 语义 | 终态 |
|---|---|---|---|
| **本地执行态** | `LocalExecState` | 本节点对这条指令"自己那一份"做到哪了：`NOT_STARTED → SELF_RUNNING → SELF_DONE`，或 `SELF_FAILED` / `SELF_CANCELLED` / `COMPLETED` | `SELF_FAILED`、`SELF_CANCELLED`、`COMPLETED` |
| **指令级** | `CommandStatus` | 服务端视角的整条指令：`PENDING → RUNNING → PARTIAL → COMPLETED / FAILED / TIMEOUT / CANCELLED` | 后四个 |
| **单个子交付** | `AssignStatus` | 每个直接子一条（不含 `PARTIAL`）：`PENDING / LEASED / DONE / FAILED / TIMEOUT / CANCELLED` | 后四个 |

## 四、指令的完整生命周期（主干）

这是整个系统的核心链路，一条指令从提交到终态要经过 **9 个关键节点**，每一步的落地顺序都影响崩溃后的可恢复性：

```
                     ┌─────────────── 发起节点（Origin）───────────────┐
  ①  POST /v1/commands
        │  验 target（只接受 SUBTREE）→ 验 origin 签名（内联 OriginCert 离线验）
        ▼
  ②  EnsureCreated ← 单事务：meta.next_cmd_seq++ + CommandRecord + 全部 Assignment
        │  返回 202（**创建事务提交后才返回**，本地执行与子树分发异步进行）
        ▼
  ③  SELF_RUNNING 先落盘 ──► ④ 执行（Executor.Run）
        │                        │
        │                        └─► 成功 → MarkSelfDone（SELF_DONE + 结果）
        │                            失败 → terminal(SELF_FAILED)
        ▼
  ⑤  waitChildren 状态机（子树聚合）
        │   进入顺序：重建上下文（child_reports）→ 审退出原因标记 → 命中对账
        │            → 判空 → 写 RUNNING
        │   三个唤醒源：子报告到达（ev）/ Deadline timer / 带 jitter 的 tick
        ▼
  ⑥  Aggregate（TREE / MERGE / SUM / COUNT / CUSTOM）+ EvaluatePolicy（OnFailure）
        │   NotDone > k ? DeadlineHit ? → 是否阻断
        ▼
  ⑦  terminal() ← 单事务：local_state + CommandRecord.Status + 结果归宿
        │   sink == SELF → results（本节点就是聚合终点）
        │   sink == UPSTREAM → pending_result（先落盘，再上报）
        ▼
  ⑧  reportUpstream → 按字节数自动选路
        │   ≤256KB 内联 Report ｜ ≤64MB StreamResult 分片 ｜ >64MB 落对象存储回引用
        │   收到 ok = true（= **已持久化接受**）才清理 pending_result
        ▼
  ⑨  父节点 acceptChildReport ← 单事务：写 child_reports 权威副本 + 置 Assignment 终态 + 记生效 attempt
        │
        └──► 沿树逐层向上，根节点把最终聚合结果写入 results
```

### 4.1 几个"不能妥协"的顺序约束

| 约束 | 为什么 |
|---|---|
| `SELF_RUNNING` **先落盘再执行** | 这是 `OnRestart` 回调的**唯一触发条件** —— 崩溃恢复时才能区分"没开始"和"执行到一半" |
| 报结果**先落 `pending_result` 再发送** | 发送成功但进程崩了 → 重启后仍能补报；反过来就会丢结果 |
| `ok = true` = **已持久化接受** | 父端收到报告先落权威副本再回 ok，子端收到 ok 才清理 —— 两端都不会丢 |
| 终态写**只在一个事务里** | `local_state` / `CommandRecord.Status` / 结果归宿三者原子，不存在"状态变了但结果没落"的中间态 |
| 分发时**父端权威水位** | 不信客户端上报的 `since_seq`，取 `max(客户端, 父侧)`，且水位**只增不减** —— 防重放也防回退 |
| 取消**只置标志** | 终态与 `children` 一律由持有 `childrenBuf` 的那个协程写，避免并发写聚合树 |

### 4.2 下发即执行（本项目的一处有意简化）

环境是"**父节点下发、子节点直接执行**"，所以：

- `Target` **只保留 `SUBTREE`** 一种语义 —— 收到任务的节点一律执行本地部分，框架**不做**任何按路径 / 标签的筛选；
- **谁都能当发起者**：任何配了 `api.http_addr` 的节点（判定不看角色）`POST /v1/commands` 之后，
  它自己就是这条指令的 `OriginID` —— 于是"这棵子树"以**它**为根，结果只落在它 + 它名下子树里：
  `handle.go` 的 `OriginId == 本节点 ⇒ sink=SELF` 让它的结果**不上报给自己的父**，祖先对这条指令一无所知
  （拿 ID 去父节点查是 `NOT_FOUND`）。验这件事：`test/from-any-node.sh`；
- 提交时显式给 `NODE`（点对点）或 `SELECTOR`（标签选择器）→ **HTTP 400 `ERR_TARGET_NOT_SUPPORTED`**；
- 好处：**结构上不可能"静默漏支"**（这是树形分发最难的故障类型）；
- `waitChildren` 仍保留"**应发未发**"对账兜底，覆盖对账窗口内新注册进来的子节点；
- proto 里字段与枚举值都保留，将来要恢复点对点改动面很小（提交校验 + 建 Assignment 的范围）。

## 五、聚合语义与失败判定

### 5.1 五种聚合策略

| 策略 | 行为 | 典型用途 |
|---|---|---|
| `TREE`（默认） | **保留层级**的树形结构：每个节点的结果与它子节点的聚合结果嵌在一起 | 需要"谁做了什么"的完整画像 |
| `MERGE` | 把自身与子节点的聚合结果合并（对象浅合并 / 数组拼接） | 汇总多份同构报告 |
| `SUM` | 数值求和（自 + 子） | 计数类汇总 |
| `COUNT` | 计数：自身计 1，每个 DONE 子按其已聚合计数值累加 | "覆盖了多少节点"（5×3 实测 = **121**） |
| `CUSTOM` | 走注册的自定义聚合器（`aggregate_name` 必填、逐跳透传） | 业务专属汇总 |

### 5.2 失败策略的精确判定公式

```
NotDone   = |{o ∈ Outcomes  : o.State ∈ {FAILED, TIMEOUT}}|
          + |{p ∈ ParentJudged : p ∈ {FAILED, TIMEOUT}}|     ← 父侧判定的终态也要算
Total     = |Outcomes| + |Unreported|                        ← 等待集合大小
TOLERATE_PCT(p) 的分母 = Total                                ← 不是 |Outcomes|

ALL_MUST_SUCCEED : NotDone > 0        → 阻断
TOLERATE_N(k)    : NotDone > k        → 阻断（**严格大于**：k=2 表示最多容忍 2 个非 DONE，第 3 个才 FAILED）
TOLERATE_PCT(p)  : NotDone / Total > p → 阻断
BEST_EFFORT      : 恒不阻断

DeadlineHit（超时）**压过一切**：无论哪种策略，超时即阻断
```

实测验证了这个 `>`（而非 `≥`）的边界：4 层 × 2 子、让第 4 层 8 个节点失败 → `TOLERATE_N:2` **COMPLETED**（`failed[] 8`）、`TOLERATE_N:1` **FAILED**。

### 5.3 失败的三种归类

| 归类 | 含义 | 是否进聚合 | 是否进背书链 |
|---|---|---|---|
| `failed[]` | 明确失败的子（有报告，状态 FAILED/TIMEOUT） | ❌ 不进聚合值 | ✅ |
| `Outcomes` 里的 DONE 子 | 正常完成 | ✅ | ✅ |
| `ParentJudged` | **父侧自行判定**的（重跑次数耗尽，拿不到子报告） | ❌ | ❌（没有 `Report.Sig`，硬塞就是伪造背书）—— 但**计入 `NotDone`** |

> 最后一条是关键：如果只统计 `Outcomes`，会出现"有子失败、整条指令却判成功"的漏洞。

## 六、结果通道与查询

### 6.1 上报三级自动升降

| 结果大小 | 走法 | 可靠性设计 |
|---|---|---|
| ≤ 256KB | 一元 `ReportResult` 内联 | 报告先落 `pending_result`，收到 `ok` 才清理 |
| ≤ 64MB | `StreamResult` 双向流分片 | `StreamBegin` 先拿许可（校验 assignment 存在 + attempt 非过期 + 总片数合法）→ 逐片验签 → 收齐校验 → 中途 `missing` 精确补片 → `final` 确认 |
| > 64MB | **落对象存储**回 `ResultRef` | 本地文件系统 `objects/<sha256[:2]>/<sha256>`，摘要寻址 + 原子写；父端按引用取回并**校验摘要** |

### 6.2 查询的回程路由（三段式）

```
入口节点 ──上行──► 沿父链找结果索引 ──► 定位持有者
                                            │
                                            ▼ 沿 owner_path 下行
                                        持有者节点（results 里有这条）
                                            │
       ◄────── 沿 reqID → 上游跳 的转发表「反向原路回」──────┘
```

- 结果 > 256KB 时：先回元数据（`has_data`），再沿同一回程发 `QueryData` 分片（逐片 gzip + crc32 + **持有者身份签名**、**首片带证书链**供入口离线验链）；
- 校验失败返回"**校验失败**"而不是 `NOT_FOUND` —— 避免把"数据损坏"误报成"没这条"；
- 超过 `query.query_response_max_bytes` 时降级为对象存储引用。

## 七、健康检查与指令轨迹

同一接口两种模式（`GET /v1/health`）：

| 模式 | 触发 | 返回 |
|---|---|---|
| **健康度** | `command_id` 为空 | 每节点的 `checks[]`（磁盘 / 在途 / 结果积压 …）+ `SubtreeSummary` 逐层累加 + `anomalies[]` |
| **指令轨迹** | `command_id` 非空 | 每个节点对这条指令的 `role`（`TRACE_SELF` / `TRACE_DESCENDANT` / `TRACE_BOTH`）+ `local_state` + `status` + 子树 `TraceSummary` |

递归的三条硬规则：

1. `depth` 逐跳递减（`-1` = 不设上限）；
2. `timeout_ms` **逐跳只减不增** —— 每跳给下一跳的预算是"本跳剩余 − 150ms 执行余量"（这一条踩过坑：早期每跳都用整个预算，4~5 层树必然超时）；
3. `detail` 只控制"是否回完整对象"，**汇总（`SubtreeSummary` / `TraceSummary`）在任何情况下都必须回传** —— 否则父端无法累加出整棵树。

可信性：每节点用自己身份密钥签响应，父端做**四步校验** —— ① 验签 → ② 证书链能到根（mTLS 已完成）→ ③ 证书有效期 → ④ 证书身份 == NodeID。

稳定性：按查询重量用**三把锁单飞**（同类查询在途即拒 429），且整个递归**跟随 HTTP 请求的 `ctx`** —— 调用方一放弃就停止扇出与等待（这一条也踩过坑：早期不跟随 ctx，被丢弃的扫描会在后台堆积把后续请求挤住）。

实测：121 节点全树 `depth=-1` → `total=120 healthy=120 degraded=0 unhealthy=0 unreachable=0`。

## 八、安全体系

### 8.1 身份与 PKI

- **NodeID = UUIDv7**（时间有序，便于排序与日志定位）；
- **密钥 = Ed25519**，用 CSPRNG 生成，**绝不从 GUID 派生**；
- **PKI 与系统树同构**：每个节点的身份证书由**它的直接父**签发，证书链一律**带全到根**；
- **双密钥隔离**：有子节点的节点额外持一张**独立的 CA 证书**（`CA:TRUE`，含 CA 公钥），身份密钥与 CA 密钥互不牵连（一把泄露不连累另一把）。

> 与方案 7.7 的差异：方案写的是"CA 密钥按需生成 → 向父重签自身证书为 `CA:TRUE`"。这样"身份密钥"和"CA 密钥"会落在同一张证书上，而子证书由 CA 密钥签发、其公钥却不在父的身份证书里，**标准 x509 链校验不成立**。改为"额外签发一张独立 CA 证书"后，链校验成立，且双密钥隔离与"PKI 与树同构"两个性质都不变。

### 8.2 启动硬约束：私钥 + 公钥必须预置

**程序绝不生成密钥**。启动时读不到就 `REFUSE TO START` 并非零退出。完整校验链（15 个负向用例全 PASS）：

```
私钥文件存在且可解析（Ed25519 / PKCS8 / 裸 seed）
  ↓
公钥文件存在且可解析（PEM PKIX）
  ↓
私钥 ↔ 公钥 ↔ 证书公钥  三者一致
  ↓
证书身份（CN 优先、SAN URI 兜底） == 配置里的 node.id
  ↓
证书未过期 + 证书链能验到 ca_cert_paths[] 任一信任锚
（**信任锚口径是"你的父"**：放父的 certs/node.crt.ca 即可，不需要根；
且在**入网成功后可以由本节点自己的证书链自举** —— chain[1:] 登记成锚，此档 ca_cert_paths 可整段不写）
  ↓
有子节点的节点：CA 私钥 + CA 证书必须预置，且 CA 证书要过 IsCA / keyUsage certSign / 有效期 / 链到锚 / CN 含 nodeID
```

### 8.3 传输与逐跳可信

| 层 | 机制 |
|---|---|
| 传输 | gRPC over HTTP/2 + **TLS 1.3** + mTLS 双向认证 |
| 链校验 | 客户端对 `ca_cert_paths[]` **多锚逐个尝试**（为将来的根 CA 轮换留口），锚池在入网后还会并入**自身证书链自举出的 CA**（`ChainAnchors`）；同时校验对端证书身份 == 期望 NodeID |
| 下行 | **逐跳重签名**：每个子拿到的 `Command` 都有专属 `HopChain`（对"即将发出的内容"取 Digest，**先签后追加**）；子节点做四项校验（ChildID / ForwarderID / Digest / Sig） |
| 上行 | **背书链**：`ChildAttest`（含 `Descendants`）；`AttestDepth`：不传 = 1，**显式 0 = 无上限（全树背书）** |
| origin | origin 签名只覆盖**创建后不可变**的字段，用内联 `OriginCert` **离线**验（不需要回连根） |
| 委托 | `ReqAuth`：入口签一份短时委托（`ViewerID` / `EntryCert` / `EntrySig` / `NotAfter` / `Kind` / `ParamsHash`），**逐跳原样透传**，每跳离线验链验签后按**自己的** `health_viewers` / `query_viewers` 白名单决定是否服务；拒绝落审计 |

`ParamsHash` 只绑定**跨跳不变**的字段（`command_id` + `detail` + `Kind`）—— 因为 `depth` / `timeout_ms` 每跳都在变，绑进去会导致逐跳校验必然失败。

### 8.4 证书生命周期：程序签发/续期 + 变更自动重载

证书这块的职责划分（**签发与续期都在程序里**）：

| 谁 | 负责什么 |
|---|---|
| **程序** | **签发**：父节点给子节点（以及其它客户端）签发，走运行期入网（私钥不出对方机器）；**续期**：生命期 2/3 处换发 —— 子由**父**签（`maybeOfferRenew`），**根由自己签**（`startSelfRenewLoop`，启动时若已进窗口也先续再启动）；启动强校验；**发现文件变更就重新加载**（fail-safe） |
| **部署时准备一次** | **根节点的自签材料**（根没有父可以签发它）：根 CA 证书 + 根自身的身份证书 |

**运行期入网（父签发子）**：

```
子 EnrollChallenge → 父下发一次性 nonce（绑定 父ID + 子ID）
子 用**自己私钥**签 (nonce|父ID|子ID)  = 私钥持有证明 PoP
子 提交 身份公钥(+CA公钥) + 入网许可 + PoP
父 校验 许可 / 白名单 / nonce 未用过 / PoP → 用**自己 CA 私钥**签这两个公钥
子 校验响应（身份是我、公钥匹配本机私钥、链能到信任锚）→ 原子写 certs/ → 热切换 → 正常 mTLS
```

三条硬规则：

1. **私钥不出本机**：请求只有公钥、响应只有证书；程序既不生成也不接收私钥（`-genkey` 是显式的部署工具，启动路径绝不生成）；
2. **许可不是唯一门槛**：还要 PoP —— 拿到 token 但没私钥也签不出有效证明；
3. **父端 fail-safe**：没配 `enrollment.token` → **拒绝一切入网**（唯一授权判据；
   `allow_ids` 白名单**已删除** —— 它挡不住"自报一个公开的 ID + 自建一对密钥"。
   想限定"这次准入给谁"，正确做法是每节点一枚一次性许可）。

**热重载**：

| 维度 | 设计 |
|---|---|
| 检测 | 稳态只 `stat`（size+mtime，微秒级、零读 IO）；`stat` 变了才读内容做二次确认（避免"仅 touch"误触发）；**轮询加 ±20% 抖动**，同机多节点不会形成 IO 突发 |
| 触发 | 轮询（默认 30s，下限 5s）+ `SIGUSR1`（脚本换证后一行 kill 即秒级生效） |
| 生效 | 信任锚/对端证书 → 只影响新连接（服务端按 `GetConfigForClient` 每次握手取当前信任锚）；**本节点身份证书/私钥**变了 → 主动重连一次（可设 `lazy` 关掉主动重连） |
| 安全 | **fail-safe**：格式坏 / 身份不符 / 链不通 / 已过期 → 保留当前证书继续服务并打 ERROR；指标 `cert_reload_total{result=ok\|failed\|missing\|nochange}` |
| 自愈 | 证书文件被删 → 子节点自动重新入网补回；根节点继续用内存旧证书（记 `missing`） |

> 为什么"两套判据"很重要：最初实现每次轮询都读全部证书/密钥内容做摘要。在"同机上百个节点"的压测里，
> 这会让 121 个节点在同一个 tick 一起读盘，形成读 IO 突发，把正常的指令分发拖慢到超时。
> 改成"先 stat、变了才读"之后，整轮慢轮询从 99 次降到 8 次（合计约 0.2s），稳态开销回到可忽略。

### 8.5 吊销与续签

| | 机制 |
|---|---|
| **吊销（CRL）** | 版本号由**该子节点的直接父**维护、单调递增（只应用更高版本）；发送方用身份密钥签名；逐跳转发；子重连即 `CRLReq` 取全量对齐；服务端**拦截器 + 连接建立点双重拦截**；`GET /v1/crl` 查看、`POST /v1/revoke?node=` 吊销 |
| **续签（子 / 中继）** | 父在子 Connect / RESUME 时检查剩余有效期，**进入生命期 2/3 窗口即换发** `CertRenewOffer`（**只换证书不换密钥** —— 已有背书链、origin 验签、CRL 条目全部照旧）；子收到后原子替换证书文件 + `TLSContainer` 热切换 + 重连握手；子侧另有每小时主动调度 |
| **续签（根）** | 根没有父，所以**自己给自己签**：`startSelfRenewLoop` 每小时检查，进窗口就用自身 CA 重签（`ReissueFor` 同一身份 + 同一公钥）；**启动路径也会先续再校验**（`loadIdentity` 的 selfRenew 开关），因此"停机很久导致证书过期"也能自己救回来，日志里会有一行"证书已自签续期" |
| **CA 证书轮换** | CA 证书**也能在线轮换**：中继向**父**申请（`CertRenewReq.want_ca` + 提交当前那张 CA 证书以证明"同一把密钥"），根自己续（`ReissueCAFor`）。只换证书、不换密钥 ⇒ **下级手里的旧 CA 证书在有效期内仍然有效、`trust/` 不用重新分发、下级也不用重新入网**。根走"先续 CA 证书、再用新 CA 证书重签身份证书"两步（顺序不能反）。指标 `ca_rotate_total{result}` |
| **有效期口径** | 身份证书 **30 天**、CA 证书 **10 年**（都可用 `security.identity_cert_days` / `security.ca_cert_days` 覆盖，默认值 = 历史行为，都不进 `config_hash`）。续签窗口在生命期 2/3 处 ⇒ 身份证书每约 20 天换一次。CA 证书给得长是因为它是信任锚链的一环；但它**不再"不参与续期"** —— 轮换能力已具备，把 10 年改成 1 年是安全的 |
| **换 CA 密钥仍要重分发** | 上面的轮换只换**证书**。真要换 **CA 密钥**（真换 CA）仍需全树重新分发 `trust/`；可借"信任锚双活"推进：`ca_cert_paths` 同时放新旧两张根证书，等所有子都换完再撤旧的 |
| **自签的边界** | 有父的节点**不许自签**（`canSelfRenew` 拦截）：它的证书必须由父签发，自己签自己等于自授权 |
| **宽限窗口** | TLS 层接受"过期 ≤ 7 天"的证书（否则连不上、也就没机会换证），但标记为 renewal-only；**应用层拦截器只放行注册 / 续签相关帧**，其余 RPC 一律拒 |

### 9.1 数据布局

```
<data_dir>/
├── node.yaml              配置（唯一人写的文件）
├── state.dat              运行状态：临时文件 + fsync + rename 原子写
├── state.db               bbolt 账本（13 个桶）

│   └── ca.key             本节点的 CA 私钥
├── keys/
│   ├── id_ed25519         身份私钥（必须预置）
│   └── id_ed25519.pub     身份公钥（必须预置）
└── objects/               对象存储：objects/<sha256[:2]>/<sha256>
```

### 9.2 恢复逻辑

| 场景 | 恢复动作 |
|---|---|
| 进程重启（本地有未终态指令） | `reactivatePending`：未终态的重跑、已终态但有结果未上报的补报 |
| 与父断线重连 | `Reconcile`：上报本地未终态指令（完整 wire `Command`）→ 父验 origin + 末条 hop 指向自己 → 与父持有的派生结果**逐字节比对**，一致则重置 Assignment 重投、**不一致即拒绝并记审计**、父无记录则按子上报内容重建 |
| 子长期不出现 | 驱逐扫描：先把该子名下未终态 Assignment 的**指令体归档**到 `evicted_children`，水位打 `evicted` 标记使其**退出保留水位计算**；该子回来对账成功后清归档；归档保留期到期连同水位条目一并回收 |
| 结果太大没传完 | `pending_result` 周期重发 + 每次 `FetchCommands` 顺手重发（单飞 + 批量上限 + 指数退避） |

### 9.3 保留水位（什么能删、什么不能删）

```
retention_floor = min( min{FetchedCmdSeq},          ← 所有子都已拉走的
                       min{未终态 Assignment 的 LocalSeq} )  ← 还有活儿没干完的
```

驱逐的子（`evicted = true`）退出第二项的计算 —— 否则一个长期离线的子会把整棵树的指令日志永久钉住。指令日志清理只删 `LocalSeq < floor` 且超过 `audit_retention` 的记录。

### 10.2.1 `node.id` 的解析（ADR-050）

`node.yaml` 对程序**始终只读**，`node.id` 也可以留空 —— 程序按下列顺序取（前一个命中即停止）：

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | `node.yaml` 里的 `node.id` | 显式指定，最高优先 |
| 2 | **已签发证书的身份**（CN 优先、SAN URI 兜底） | 证书就是身份 ⇒ **根节点不必在配置里写 id** |
| 3 | **`state.dat` 的 `self.id`** | "还没拿到证书"那段窗口里的身份锚点 |
| 4 | 生成 UUIDv7 | **在上线前**写进 `state.dat`（不是 `node.yaml`），此后固定 |

**为什么是 `state.dat` 而不是回写配置**：`node.yaml` 是"人写的、可进版本管理"的配置，程序碰它就把配置变成了状态
（ADR-005）。NodeID 属于**运行期状态**，`state.dat` 正是它的归宿 —— 只由程序写、可丢弃重建、且已被 `.gitignore` 覆盖，
因此**不需要给 ADR-005 开任何口子**。落盘时机很关键：`state.dat` 此前只在周期（默认 30s）与优雅退出时写，
所以解析出**新** ID 时，`internal/node` 会在**上线前**补一次落盘，否则"首启 30s 内崩溃"会换掉身份。

| 情形 | 行为 |
|---|---|
| `state.dat` 与证书身份不一致 | 以**证书**为准，并在启动日志告警（否则必然过不了启动强校验） |
| 生成值 | 在上线前写进 `state.dat`（此后固定，跨重启稳定）；程序**绝不回写 `node.yaml`** |
| 想固定 ID | 在 `node.yaml` 显式写 `node.id`（程序永不改写它） |
| `node.id` 留空时 | 程序上线前把它写进 `state.dat`；想知道实际拿到的 ID，看启动日志或读 `state.dat` 的 `self.id` |

## 十一、HTTP API 完整参考

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/v1/commands` | 提交指令。本节点即 `OriginID` 与聚合终点；返回 `202` + `command_id` |
| `GET` | `/v1/commands/{id}` | 结果查询（跨节点沿路径前缀路由到持有者；大结果自动分片回传） |
| `POST` | `/v1/commands/{id}/cancel` | 取消（进程内标志 + ctx.cancel，终态由持 `childrenBuf` 的协程写） |
| `POST` | `/v1/commands/{id}/retry?node=<childID>` | 子节点重跑（`RetryNode`，失败次数归自身）；**预算用尽时**该子被父判为 `FAILED`，返回 `200 {retried:false, judged:"FAILED"}` 而不是一个含糊的失败 |
| `GET` | `/v1/health[?command_id=&depth=&detail=&timeout=]` | 健康度 / 指令轨迹双模式；返回体含本节点 `node_name` / `node_remark`，`detail=true` 时每个子节点也带（ADR-051，逐层可见） |
| `GET` | `/v1/health/summary` | 同上（拓扑摘要视图） |
| `GET` | `/v1/tree` | 本节点视角的拓扑（含对象存储目录等）；本节点与每个直接子都带 `node_name` / `node_remark` |
| `GET` | `/v1/crl` | 当前 CRL（版本 + 吊销 GUID 列表） |
| `POST` | `/v1/crl?node=<GUID>` | 吊销某节点：写本地 CRL、版本 +1、推送给全部直接子 |
| `GET` | `/v1/forget?node=<GUID>` | **清理预览**：某直接子会不会被允许清理、会被删掉哪些条目（只读，不改数据） |
| `POST` | `/v1/forget?node=<GUID>[&mode=garbage\|stale][&force=1][&purge=1]` | 清理失效的直接子节点：一条写事务里删 assignments(+反向索引) / child_watermark / evicted_children，事务后 `Reg.Remove` + `saveState()`；在线的一律拒绝 |
| `POST` | `/v1/forget?all=1[&mode=&force=1]` | 批量：对本节点名下所有直接子逐个尝试，逐条返回结果 |
| `GET` | `/metrics` | Prometheus 文本指标 |
| `GET` | `/v1/healthz` | 存活探针（**永远免认证**） |

**访问控制（写接口）**：表里 `POST` 那几条是**写操作**，其中 `/v1/crl`、`/v1/forget` 是不可逆的运维动作
（吊销节点 / 删注册状态），`/v1/commands` 则会让整棵子树干活 —— 所以它们不能是"能连上端口就能调"。
实现见 `internal/node/apiauth.go`，口径五步：`/v1/healthz` 永远放行 → 读请求默认放行
（`api.auth.protect_reads: true` 可一并收紧）→ mTLS 客户端证书（`api.tls.trust_client_cert`）→
**回环来源**（TCP 对端是 127.0.0.1/::1，**且不带转发特征头**，或转发链还原后仍是回环）放行 →
其余写请求必须带共享密钥的 HMAC 签名（时间戳 ±60s + nonce 防重放），**没配密钥就一律拒绝**。

签名除了"内容没被改"，还钉住三件事：**接收方**（`X-Treecmd-Audience` = 目标 node_id，挡"把签好的
请求转发给共享同一密钥的另一个节点再执行一次"）、**Host**（挡换入口投递）、**通道绑定**
（`X-Treecmd-Channel-Binding` = 服务端证书哈希，挡中间人换自己的证书）。配了密钥时**响应也签名**
（`X-Treecmd-Response-Signature`），明文链路上也能验出"响应是不是那个节点、针对这次请求回的"。
密钥**不进 `config_hash`** 且请求时现读，换密钥不用重启；远程调用用 `scripts/api_call.py`
（`--audience` 必填）。完整口径与边界见 README「访问控制：写接口的本机豁免与远程签名」，
端到端验收见 `test/api-auth.sh`（49 项断言）。

提交请求体（`POST /v1/commands`）：

```jsonc
{
  "type": "echo",              // 执行器类型
  "payload": "aGVsbG8=",       // base64
  "target": {"mode": "SUBTREE"},   // 只支持 SUBTREE（NODE/SELECTOR → 400）
  "aggregate": "TREE",         // TREE | MERGE | SUM | COUNT | CUSTOM
  "aggregate_name": null,      // aggregate=CUSTOM 时必填
  "on_failure": "ALL_MUST_SUCCEED", // 或 TOLERATE_N:2 / TOLERATE_PCT:0.1 / BEST_EFFORT
  "raw_children": false,       // 是否把子的原始结果一并返回（CUSTOM 可能需要）
  "attest_depth": null,        // 不传 = 1；显式 0 = 无上限（全树背书）
  "idempotent": null           // 幂等键
}
```

执行外部脚本时，唯一的那个参数就是一个 JSON（`script` 是文件名，`params` 由脚本自己解释）：

```jsonc
{
  "type": "script",
  "payload": "<base64 of {\"script\":\"hello.sh\",\"params\":{\"who\":\"tree\"}}>",
  "aggregate": "TREE"          // 保层级；想换形状改这一项（MERGE / SUM / COUNT / CUSTOM）
}
```

`sha256` **不用自己写**：发起节点会在签名之前把本地脚本的哈希注入载荷（因此它不可篡改），
并且如果本节点上没有这个脚本，提交期就会直接被拒。

## 十二、协议参考

### 12.1 服务（`api/proto/node.proto`，715 行，唯一协议约定）

```protobuf
service NodeService {
  rpc Connect(stream UpFrame) returns (stream DownFrame);        // 控制面：注册/心跳/通知/健康/查询
  rpc FetchCommands(FetchRequest) returns (FetchResponse);       // 拉模式投递
  rpc ReportResult(Report) returns (ReportResponse);             // 小结果内联上报
  rpc StreamResult(stream StreamFrame) returns (stream UploadAck); // 大结果分片上行
}
```

### 12.2 帧类型

**上行 `UpFrame`**：`Register` / `Resume` / `Heartbeat` / `LeaseRenew` / `CRLReq` / `CertRenewReq` / `Reconcile` / `LocalBusy` / `InflightHint` / `ResultIndexUp` / `HealthResp` / `QueryResp` / `QueryData`

**下行 `DownFrame`**：`RegisterAck` / `CommandNotify` / `CommandCanceled` / `TerminalNotice` / `HealthReq` / `QueryReq` / `RevocationList` / `CertRenewOffer` / `ConfigPush` / `HeartbeatAck`

> `HeartbeatAck` 承载 `t2`/`t3` 供子节点算 EWMA 时钟偏移，且 `terminal[]` 是"**续租响应必须回带终态**"这一必经路径的载体 —— 它是同一条必经路径的另一半，不另发独立帧。本帧不参与签名 / 摘要（时钟样本不需要不可否认性）。

### 12.3 canonical 编码（可靠性的地基）

- 序列化：`proto.MarshalOptions{Deterministic: true}`；
- `repeated` 取摘要前**显式按 NodeID 的 16 字节大端升序**排序（注意：**不是字符串字典序**）；
- 时间字段一律 `google.protobuf.Timestamp`；
- 需要区分"未设置"与"显式 0"的标量一律 `optional`。

> 这套口径决定了"同一个 `(cmd, child, attempt)` 的派生 `Command` 逐字节一致"，而逐字节一致又是全部签名校验、重投幂等、`Reconcile` 比对的前提。

## 十三、命令行与工具链

### 13.1 `treecmd-node`（真实部署用）

```bash
treecmd-node -config <node.yaml> [-log-level debug|info|warn|error]   # 启动
treecmd-node -enroll -config <node.yaml>     # 只做一次入网并写证书，然后退出
treecmd-node -genkey -keydir keys [-with-ca] # 一次性生成密钥对（显式部署工具）
# 配置样例：examples/node.yaml（唯一权威）—— 头部"按角色最简起步"，正文逐字段标角色与默认值
# SIGUSR1 = 立即重载证书；SIGHUP = 配置热更；SIGINT/SIGTERM = 退出
```

> 命令面只有这三条 —— **没有独立的"检查"子命令**：配置与身份材料的强校验就在启动路径上
> （`load config failed` / `node init failed: REFUSE TO START ...`，非零退出）。
> 想"部署前先看一眼"就直接启动：起不来就是有问题，日志里写着原因。

配套：`scripts/start_node.sh <node.yaml> [start|stop|status|reload|conf]`；
样例配置只有一份：`examples/node.yaml`（根 / 中继 / 叶共用，按字段前的角色标记增删）；
阅读顺序与部署清单见 `examples/README.md`。

## 十四、已知限制与未实现（明确标注）

均**不在主链路正确性路径**上，按影响排序：

| 项 | 现状 | 需要什么才能补齐 |
|---|---|---|
| 根 CA 轮换的双签过渡期 | 多信任锚（`ca_cert_paths[]`）已支持 | "同时信任新旧根 + 全树滚动重启"的运维编排 |
| 对象存储的跨节点取回 | 引用只保证"同一节点可取回"（本地文件系统） | 换成 S3 / 共享盘 |
| `evicted_children` 的跨节点取回 | 归档在本节点本地 | 共享存储 |
| `AttestDepth ≥ 2` 的递归背书验签 | `Descendants` 已回传，父端默认只验直接子层 | 审计态的递归验签开关 |
| 健康请求的应用层限流 | `health.rate_limit_per_sec` 已在配置里 | 接一个限流器（单飞互斥已实现） |
| `ConfigPush` 中心化分发 | 仅支持父手写 `overrides` | "根推到全树"的编排 |
| 规模验证 | 已测：同进程 **121 节点**、多进程 **15 进程** | 方案里 1000 节点的估算需要真实多机压测 |
| 点对点下发（`NODE` / `SELECTOR`） | 有意下线 | 恢复成本很小（提交校验 + 建 Assignment 范围），proto 字段都还在 |

## 十六、快速上手（复制即跑）

```bash
cd /Users/yujinyuan/code/一个想法/treecmd

# 1) 构建（全项目只有一个可执行文件：单节点入口）
go build -o bin/treecmd-node ./cmd/node

# 2) 抄一份样例配置（唯一一份：头部有"按角色最简起步"，正文逐字段标角色与默认值）
cp examples/node.yaml node.yaml

# 3) 一次性生成密钥对（程序启动路径绝不生成密钥，这是显式的部署工具；有下级就加 -with-ca）
./bin/treecmd-node -genkey -keydir keys -with-ca

# 4) 启动（配置/材料有问题会 REFUSE TO START 并非零退出，原因写在日志里）
./bin/treecmd-node -config node.yaml

# 5) 起停 / 换证后重载 / 配置热更
./scripts/start_node.sh node.yaml            # 启动（后台起、写 node.log / node.pid）
./scripts/start_node.sh reload node.yaml     # = kill -USR1：证书脚本换证后立即生效
./scripts/start_node.sh conf   node.yaml     # = kill -HUP：配置热更
./scripts/start_node.sh stop   node.yaml

# 6) 用 HTTP API 做手工验证（地址取自 node.yaml 的 api.http_addr）
curl -s localhost:18443/v1/tree
curl -s 'localhost:18443/v1/health?depth=-1&timeout=20s' | python3 -m json.tool | head -40
curl -s localhost:18443/metrics | head -20
curl -s -XPOST localhost:18443/v1/commands \
  -d '{"type":"echo","payload":"aGVsbG8=","aggregate":"TREE"}'
```

> 从零把一棵树部署起来的完整步骤（根自签 CA → 子节点入网换证 → 整树收敛）见 `docs/手动部署指南.md`。
