## 1. PKI 中 CA 证书独立一张

### 现状

- 有子节点的节点额外持有一张 `CA:TRUE` 的 CA 证书（含 CA 公钥），由**父的 CA** 签发；
  子节点身份证书由**本节点的 CA 密钥**签发；子节点上链 = `[子身份证书, 父CA证书, …, 根CA]`。
- 启动校验 `ValidateStartup` 只做了"CA 私钥 ↔ CA 证书公钥配对"，**没有校验 CA 证书本身**。

### 判断

方案的"向父重签自身证书为 `CA:TRUE`"存在一个**不可校验的闭环**：重签后的证书里是**身份公钥**，
而子节点证书是用**CA 私钥**签的 —— 校验方拿到的链上没有任何一张证书持有 CA 公钥，标准 x509 链必然失败。
所以独立 CA 证书不是"绕开方案"，而是**把方案的双密钥意图落到可校验的结构上**。这条保留。

**但**：既然 CA 证书是信任链的一环，就必须像身份证书一样被强校验，否则一张被替换/过期的 CA 证书
会在运行时才暴露（子节点注册失败），而不是启动时就 fatal。

### 推荐方案（A）：保留独立 CA 证书 + 补强启动校验 + 去掉魔法路径

**A1. 补强 `ValidateStartup`**（`internal/identity/identity.go`）

```go
if id.CAKey != nil {
    // 现状：只比对公钥
    // 新增：
    //   ① id.CACert.IsCA == true
    //   ② id.CACert.KeyUsage 含 x509.KeyUsageCertSign
    //   ③ id.CACert 未过期（同样给 7 天宽限）
    //   ④ id.CACert 用同一 pool + CAChain[1:] 作为 intermediates 验到信任锚
    //   ⑤ id.CACert.Subject.CommonName 以 nodeID 为前缀（审计可读性）
}
```

**A2. 把 `<identity_cert_path>.ca` 魔法路径改成显式配置**

新增 `security.ca_cert_path`（本节点自己的 CA 证书，注意与信任锚 `ca_cert_paths[]` 区分）；
缺省仍按 `<identity_cert_path>.ca` 推导以兼容既有部署产物，但**推荐显式写**：
在你自己的 `node.yaml` 里补上这一行。

**A3. 明确"先叶子后扩子"的路线**：取**静态供给**（与 ADR-005 一致）——
运维扩子 = 改配置 + 重新签发一张 CA 证书 + 重启（自签命令见 `docs/手动部署指南.md`）。方案 7.7 的"运行时按需生成 CA + 向父重签"
只在"动态挂子"时才有价值；本实现不做，但在文档里写明"运行时不生成任何密钥"（与第 ① 条需求一致）。

### 备选

- **B（贴合方案字面）**：让父直接用**父的 CA 私钥**签子身份证书，且父的身份证书在"有子节点"时是 `CA:TRUE`。
  链变成 `[子证书, 父证书(CA:TRUE), …]`，标准校验成立，但**退化为单密钥**（身份密钥 == CA 密钥），
  与方案 7.7「双密钥互相隔离，一把泄露不连累另一把」直接冲突。**不推荐**。

### 验收

- 启动强校验对 CA 证书做同强度校验：CA 证书被换成非 CA 证书 / CA 证书签名被破坏 / CA 证书过期 → 均拒绝启动。
- 现有 mTLS 链路与树同构性质不变（5 层树照常注册、执行、聚合）。

## 3. `AttestDepth` 的 0 值 —— 真缺陷

### 现状与问题

```go
// internal/node/submit.go:138
attestDepth := req.AttestDepth
if attestDepth == 0 { attestDepth = 1 }                  // ← 0 被当成"未设置"
if req.RawChildren && attestDepth < 2 { return ERR_INVALID_ATTEST_DEPTH }
```

`Command.attest_depth` 是 **proto3 非 optional 标量**，wire 上无法区分"未设置"与"显式 0"。
方案 7.5 把 `0` 定义为**无上限（全树背书）**，且 3.15 明确 "`RawChildren=true` 时校验
`AttestDepth != 0 && AttestDepth < 2` → 拒绝"（**0 必须放行**）。
于是当前实现下 `RawChildren=true, AttestDepth=0` 会走到 `attestDepth=1 < 2` → **被误拒**，
"完整审计组合 `RawChildren=true + AttestDepth=0`" 根本用不了。

### 推荐方案（A）：改成 `optional int32`，与方案的"枚举 0 值约定"同构

**A1. proto**（`api/proto/node.proto`）

```proto
optional int32 attest_depth = 12;   // 未设置 → 默认 1；显式 0 → 无上限（全树背书）
```

生成后 Go 侧变 `*int32`，用 `has_*`（即 `!= nil`）判定，**不再靠"值是不是 0"**。

**A2. 提交侧**（`internal/node/submit.go`）

```go
depth := int32(1)
if req.AttestDepth != nil {          // SubmitRequest 的字段也改成 *int32
    depth = *req.AttestDepth
}
if req.RawChildren && depth != 0 && depth < 2 {   // 0 = 无上限，放行（修掉当前缺陷）
    return ERR_INVALID_ATTEST_DEPTH
}
```

**A3. 使用侧**（`internal/node/wait.go` 的 `buildAttest`）逻辑不变，但语义注释改成
"`AttestDepth == 0`：无上限；否则 `d + 2 <= AttestDepth` 才带 `Descendants`"。

**A4. 兼容性**：字段号不变，只是加了 presence；老 peer 发来 `attest_depth=0` 会被新实现理解为"0 = 无上限"，
**默认值语义从 1 变成 0（无上限）** —— 这是唯一的行为变化，需在 proto 注释里写清"不传 = 默认 1，传 0 = 无上限"，
并在 README 标注。若担心跨版本分叉，可一并 bump `proto_version` minor。

### 验收

- 单测/用例：`{RawChildren:true, AttestDepth:0}` → 200，且 5 层树的 `Report.Children[].Descendants` 递归到叶子；
  `{RawChildren:true}`（不传）→ 200，`Descendants` 为空（默认 1）；`{RawChildren:true, AttestDepth:1}` → 400。
- `Children=nil` 与 `Children=[]` 的摘要一致性测试向量仍成立（7.5 要求）。

## 4. `Target` 只保留 `SUBTREE`

### 判断

按你的要求做的简化（"父节点下发的任务，子节点直接执行即可"），不是缺陷。
保留 proto 字段与枚举值，将来要恢复时改动面可控。这里给出**若恢复的正确实现路径**。

### 恢复 `NODE`（点对点）的改动清单

| 位置 | 改动 |
|------|------|
| `submit.go` | 恢复 `Target.Path` 与 `IsAncestor(selfPath, path)` 的 `ERR_TARGET_OUT_OF_SCOPE` 校验 |
| `submit.go` / `EnsureCreated` / `reconcile` | 建 Assignment 时加判定：只给"路径前缀覆盖目标"的直接子建 |
| `handle.go` | 恢复"未命中 → 空自身结果 + 落 `SELF_DONE`"分支 |
| `registry` | 恢复 `IsAncestor` 判定辅助函数 |
| 测试侧 | `summarizeTree` 已能区分"参与聚合 / 命中并执行"，无需改 |

**风险**：TREE 聚合里会重新出现"空 `self` 的中间节点"，`NotDone`/`failed[]` 的统计口径需回归验证。

### 恢复 `SELECTOR`（标签）的推荐做法 —— **不要恢复"分发侧剪枝"**

方案 2.1/2.3 的剪枝依赖"子树标签摘要"，并自带一条极重的硬约束：
**绝不能用会丢元素的结构**（LRU 会把活跃子树的标签挤出去 → 假阴性 → **整支静默漏发**，
父只能等 `Deadline`，甚至误判成功）。这是本系统最难排查的一类故障。

**推荐**：把 `SELECTOR` 实现为**执行侧过滤**，父侧**不剪枝、全发**：

```
父：仍然对所有直接子节点建 Assignment（= 现在的"下发即执行"逻辑，零改动）
子：收到后自己判断 n.matches(Target) →
      命中：执行本地部分，自身结果非空
      未命中但有命中后代：只转发，自身结果记空
      未命中且无命中后代：不建 Assignment、不投递（本地剪枝，但只影响"自己的下一跳"）
```

- **正确性**：任何一跳的判定错误最多导致"多发一路、回空结果"，**不可能静默漏支**。
- **代价**：消息量从"剪枝后的子树"变成"整棵子树"，本场景（121 节点 / 40 端口）实测端到端 22s，
  多一圈空结果的开销可忽略。
- **额外收益**：`waitChildren` 的"应发未发对账"从"兜底防线"变成"纯保险"，
  标签摘要那一整套（`TagSummary` / `SummaryKnown` / 不丢元素结构）**都不需要**。

> 若将来节点规模上到 1000+ 且消息量成为瓶颈，再考虑加剪枝 —— 届时摘要必须用
> Bloom 过滤器或"限容量精确集合 + 显式清理"，并按方案 2.3 的方向性错误规则处理"摘要缺失 = 可能命中"。

## 5. `Unreported` 的口径扩展 —— 建议显式建模

### 现状与问题

`RetryNode` 次数耗尽时，父侧把该子判 `FAILED`，我把它塞进了 `Outcomes`（`Attest=nil`、不进背书链），
否则 `NotDone` 统计不到它 → 可能出现"有子失败、整条指令却判成功"。

这解决了漏洞，但**污染了 `Outcomes` 的语义**（方案 3.16：`Outcomes` = "实际收到 `Report` 的子"），
且 `WaitResult.Children`（背书链）与 `Outcomes` 的 1:1 关系被打破 —— 未来任何
"`Outcomes[i]` 必定有 `Attest`"的假设都会踩雷。

### 推荐方案（A）：把"父侧判定"显式建模成独立集合

**A1. `WaitResult` 增加一个显式字段**（`internal/node/wait.go`）

```go
type WaitResult struct {
    Outcomes   []aggregate.ChildOutcome // 严格 = "收到过 Report 的子"（与 Children 1:1）
    Unreported []string                 // 未上报：仍在等待 / 已被父侧判定终态
    ParentJudged map[string]pb.AssignStatus // 父侧自行判定终态的子 → 状态（FAILED/TIMEOUT）
    Children   []*pb.ChildAttest        // 只由"已上报子"组成，与 Outcomes 严格对应
    Cancelled  bool
    Deadline   bool
}
```

**A2. `aggregate.Context` 增加 `ParentJudged`**，`EvaluatePolicy` 的 `NotDone` 口径改为：

```
NotDone = |Outcomes 中 FAILED/TIMEOUT| + |ParentJudged 中 FAILED/TIMEOUT|
Total   = |Outcomes| + |Unreported|        # 不变；ParentJudged ⊆ Unreported
```

- `Total` 仍等于等待集合大小（`ParentJudged` 是 `Unreported` 的子集，不重复计数）；
- `NotDone` 不再漏掉"父侧判定的失败"，漏洞关闭；
- `Outcomes` ↔ `Children` 恢复 1:1，语义干净。

**A3. 改动点**：`partition()`（把 `adjudicated` 从"塞进 Outcomes"改为"记入 `ParentJudged`"）、
`buildOutcomes`、`finalize`（未上报子落 `TIMEOUT`/`CANCELLED` 时同步写 `ParentJudged`）、
`aggregate.EvaluatePolicy` 签名、`CommandTrace.Summary`（已按 assignment 统计，不用改）。

### 验收

- 构造"某子永不回报 + `RetryNode` 3 次耗尽" → `ALL_MUST_SUCCEED` 下整条指令必须 `FAILED`（当前也过，但靠补丁）；
- `TOLERATE_PCT:0.4` 分母仍 = `|Outcomes| + |Unreported|`（方案的校验例：10 子、7 上报（4 DONE + 3 FAILED）、3 未上报 → `3/10 = 0.30 ≤ 0.4 → COMPLETED`）；
- `Report.Children` 里**不出现** `ParentJudged` 的子（防伪造背书）。

## 6. 健康响应的 `SubtreeSummary` / `TraceSummary` 承载字段

### 判断

`ChildHealth.Report = nil`"，却没给"父端如何拿到子的子树汇总"的承载字段 ——
按字面实现，父端无法逐层累加出整棵树的计数。

### 推荐（A）：回写方案 + 代码保持

- 方案 4.3 的 `ChildHealth` / `ChildTrace` 各补一行：
  `SubtreeSummary summary` / `TraceSummary summary`，并注明"**`detail=false` 时也必须回传**，
  否则父端无法累加子树计数"；
- 4.3 的 `detail` 段落补一句："`detail` 只控制**是否回完整对象**，不控制汇总"。

### 备选

- **B**：`detail=false` 时让子节点回一个"只填了 Summary 的 `Report`" —— 与"`ChildHealth.Report = nil`"字面冲突，**不推荐**。
- **C**：不改，父端 `detail=false` 时子树计数只到直接子层 —— 健康度看板会失真，**不推荐**。

| 方向 | 帧 | 用途 |
|------|----|------|
| 父 → 子 `DownFrame` | `HeartbeatAck{echo_send_ts_local, recv_ts, send_ts, terminal[]}` | 心跳应答：**承载 t2/t3 供子节点算 EWMA 时钟偏移**；`terminal[]` 是 3.9「续租响应必须回带终态」的载体 |

并补三条口径说明：

1. 它**不参与任何签名 / 摘要**（与 5.4 对 `Heartbeat` 的约定一致：时钟样本不需要不可否认性）；
   将来若要把它纳入摘要，**必须先把 `renew` / `load` 子结构的字段号写死**；
2. **终态回带走 `terminal[]`，不是"另外再发一个 `TerminalNotice` 帧"** —— 二者是同一件事的两种说法，
   实现里不要重复发送；
3. `HeartbeatAck` 与 3.9 的"必经路径"是**同一个机制的两半**：取消/超时的收敛靠它，不靠主动帧。

### 备选

- **B**：把它合并进 `TerminalNotice` 帧（少一种帧）—— 但"时钟采样"与"租约确认"语义耦合，**不推荐**。
- **C**：不做 EWMA，跳过 `HeartbeatAck` —— 跨地域会因时钟漂移误判 `Deadline`，**不推荐**。
